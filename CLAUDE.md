# gdecl

Guidance for working on the gdecl framework: Godot 4 GDExtension programming in Common Lisp with ECL, without godot-cpp. User-facing documentation is in `README.md`. This is its own repository (github.com/flambard/gdecl), used by applications as a git submodule, so keep it free of anything specific to an application.

## Goal and direction

GDExtension is a low-level C interface, not meant to be used directly by application developers. gdecl's goal is to raise the level of abstraction step by step until writing a Godot application in Lisp is at least as easy as with GDScript or C#, while staying efficient. Godot is mostly used for games, which are performance sensitive, so ease of use must not cost per-frame overhead.

Principles:

- **Build up gradually.** Each layer is built on the one below it: `gd-extension-ffi` (the C interface, one-to-one), then `gd-extension-types` (builtin types in Lisp), then `gd-extension-callback` (Godot's calls into Lisp), then `gd-extension` (Lisp-style helpers), then probably a third layer on top of `gd-extension` for the highest-level concepts, such as the CLOS integration below (not decided yet). Grow the framework from what the applications built on it need, and move code from an application into gdecl once the pattern is clear.
- **Keep the lower layers usable.** An application can always use a lower layer for what the higher ones don't cover yet, or for a hot path.
- **Do the work up front, not per call.** Look up method binds, StringNames and constructors once (at initialization or registration) and cache them. Prefer `ptrcall` to Variant calls. Avoid allocating in calls that happen every frame (`_process`, `_physics_process`), e.g. by not boxing floats or creating temporary Strings. Prefer compile-time expansion (macros, code generated from `extension_api.json`) to runtime lookup and dispatch.
- **Improve gdecl as you go.** When working on an application and gdecl is missing something, or something in it could be better, add or improve it in gdecl rather than working around it in the application. Keep such changes general, not specific to the application.
- **Measure.** Before choosing a convenient but slower design for something called often, check what it costs.

Where to look for inspiration:

- **GDScript**: the API application developers know. `extends`, `@export` properties, `signal`, virtual methods such as `_ready` and `_process` that you just define, `$Node` paths, `@onready`.
- **Godot C# (`GodotSharp`)**: the closest model, a garbage-collected language binding. Engine classes are generated from `extension_api.json` as wrapper classes, with method binds cached in static fields. Builtin types such as `Vector2` are value types implemented in C#, not calls into the engine. User classes are ordinary C# classes with attributes (`[Export]`, `[Signal]`), and a source generator writes the registration code. Godot objects and managed objects are linked through a GC handle, and `RefCounted` lifetimes are tied to the managed object.

### CLOS integration (idea, not yet decided)

`define-class` (see Classes) is a first step with structs instead of CLOS classes, with a syntax that could later expand into `defclass` and methods without changing applications much.

It would be good if Godot classes were CLOS classes, so that an application writes something like:

```lisp
(define-godot-class player (sprite-2d)
  ((speed :initform 400.0 :type float :export t))
  (:signals (hit)))

(defmethod process ((self player) delta) ...)
```

Things to find out:

- **Defining classes**: a macro over `defclass`, or a metaclass (`godot-class`) through the MOP, that also registers the class with `classdb_register_extension_class`. Exported slots become properties.
- **Instances**: `create_instance_func` creates the Lisp instance next to the Godot object. Godot only holds a pointer, so the link must keep the Lisp object reachable for the GC (an index into a table, like `*bound-methods*`) and be removed when Godot frees the object.
- **Virtual methods**: generic functions (`process`, `ready`, `input`, …) whose methods are found once, in `get_virtual_call_data`, not at every call. Only report a virtual as implemented when the class has a method for it, so Godot doesn't call into Lisp for nothing.
- **Engine classes**: generate a CLOS class and functions for each Godot class from `extension_api.json`, with method binds cached. Plain (inlinable) functions are cheaper than generic functions; use generic dispatch only where the application can override something.
- **Wrapping engine objects**: the same Godot object should map to the same Lisp wrapper (instance bindings, `object_set_instance_binding`). `RefCounted` objects need reference counting tied to the wrapper's lifetime (finalizers).
- **Builtin types**: `Vector2`, `Color`, etc. as Lisp structs or specialized arrays with arithmetic in Lisp, without calls into Godot. Mind `real_t` (single precision in the `float_64` build configuration).
- **Cost of CLOS dispatch in ECL** for methods called every frame, and whether caching the effective method is enough.

Lisp can also offer what GDScript and C# can't easily: redefining functions and classes in a running game, and a REPL connected to Godot.

## Layout

- `gdecl.asd`: the ASDF system `gdecl`, with its Lisp code in `lisp/`.
- `LICENSE`: MIT.
- `lisp/packages.lisp`: the packages `gdecl-json`, `gd-extension-ffi` (nickname `gdext-ffi`), `gd-extension-types` (nickname `gdext-types`), `gd-extension-callback` (nickname `gdext-callback`), `gd-extension` (nickname `gdext`), `godot` (nickname `gd`) and `godot-utility` (nickname `gd-util`).
- `lisp/gd-extension-ffi.lisp`, `lisp/gd-extension-types.lisp`, `lisp/gd-extension-callback.lisp` and `lisp/gd-extension.lisp`: the four layers, see below.
- `lisp/godot-utility.lisp`: the package `godot-utility`, Godot's utility functions (`define-utility-functions`).
- `lisp/godot-engine-classes.lisp`: the most used engine classes in the package `godot`, Godot's API in Lisp, on top of `gd-extension` (`define-engine-class`). It's meant to hold what `extension_api.json` describes for applications to call: engine methods, enums and constants. The utility functions have their own package, `godot-utility`.
- `lisp/extension-api.lisp` (package `gd-extension`): reads `extension_api.json` at compile time, for `define-engine-method`, see Builtin types and engine methods.
- `lisp/json.lisp`: the package `gdecl-json`, a small JSON reader (`read-json-file`, `parse-json`, `json-get`) for `extension_api.json`, so gdecl doesn't depend on a JSON library. It's not one of the layers; only `lisp/extension-api.lisp` uses it.
- `src/gdecl.c`: the C bootstrap, the extension's entry point.
- `gdecl.mk`: the make rules for the whole build (Lisp and C), included by an application's Makefile.
- `src/gdextension_interface.h` and `extension_api.json`: generated by Godot, see Build.
- `package-ffi-symbols.txt` and `package-si-symbols.txt`: the symbols exported by ECL's `FFI` and `SI` packages, for reference while writing FFI code.

## Build

- `gdecl.mk` builds the application's ASDF system (`SYSTEM`) with `:monolithic t`, so its dependencies, including `gdecl`, are compiled into the same library. The output is always `$(BUILD_DIR)/application.a` with the init function `init_lib_APPLICATION` (`:init-name`), whatever the application is called. `src/gdecl.c` calls `init_lib_APPLICATION` by name; keep the two in sync.
- `gdecl.mk` finds its own directory through `MAKEFILE_LIST`, so gdecl can live at any path. It puts its own directory and the application's `LISP_DIRS` on `asdf:*central-registry*`.
- Changing `SYSTEM` doesn't make `application.a` out of date; use `make -B`.
- `gdecl.mk` then compiles `src/*.c` into `BUILD_DIR` (default `build`) and links the objects and `application.a` into `LIBRARY`. ECL's flags come from `ecl-config --cflags` and `--ldflags`; `application.a` goes before them, so before `-lecl`. The library depends on `application.a`, so Lisp changes relink it. The compiler is `CC` if set on the command line or in the environment, otherwise clang if installed, otherwise `cc`. `CFLAGS` defaults to a debug build (`-O0 -g`).
- `src/gdextension_interface.h` and `extension_api.json` are generated with `godot --dump-gdextension-interface` and `--dump-extension-api-with-docs` (`make godot-api`). They're ignored by `.gitignore`; don't edit them by hand. The Lisp code is compiled with `extension_api.json`, so `application.a` depends on it, and is rebuilt by `make godot-api`. The `EditorSettings not instantiated yet` error Godot prints while dumping is harmless.

## Startup flow

1. Godot calls `gdecl_library_init` (`src/gdecl.c`). It keeps `get_proc_address` and the class library in static variables until ECL is booted.
2. At `GDEXTENSION_INITIALIZATION_SCENE`, `initialize_gdecl_module`:
   - disables ECL's signal trapping (SIGSEGV etc.) so it doesn't conflict with Godot's handlers,
   - calls `cl_boot`, then `ecl_init_module(NULL, init_lib_APPLICATION)`. This loads the Lisp code, and the application's top-level forms register its entry point with `gd-extension:add-initialize-hook`,
   - evaluates `(gd-extension-callback:initialize get-proc-address class-library)` with `si_safe_eval`, passing the pointers as foreign-pointer objects (`ecl_make_pointer`). This is the only Lisp function the C side calls; it knows nothing about the application.
3. `gd-extension-callback:initialize` calls `gd-extension-ffi:load-interface`, which stores `*get-proc-address*` and `*class-library*`, looks up the interface functions and caches the Variant constructors. It then fills in the initialize cells and runs the initialize hooks. `initialize` and `deinitialize`, the hook lists and the initialize cells are in `gd-extension-callback`, since they're entry points from C, not for applications; `gd-extension` re-exports `add-initialize-hook` and `add-deinitialize-hook`.
4. At `GDEXTENSION_INITIALIZATION_SCENE` deinit, `deinitialize_gdecl_module` evaluates `(gd-extension-callback:deinitialize)`, which runs the deinitialize hooks (`add-deinitialize-hook`, in reverse order) while Godot can still be called, then calls `cl_shutdown`. `gd-extension` adds two hooks when it's loaded, so they run after the application's: `unregister-classes` unregisters the classes from `register-class` (last registered first, so subclasses go before their parents), then `destroy-permanent-values` destroys the StringNames and NodePaths from `new-string-name` and `new-node-path` (`sname`, `npath`, class and virtual method names). With both, Godot reports no leaked StringNames at exit (`--verbose`), also in the editor; the one orphan `Node` it reports in the editor is Godot's own, also without gdecl.

## The four layers

- `gd-extension-ffi` (`lisp/gd-extension-ffi.lisp`) maps the GDExtension C interface one-to-one: interface function wrappers, enums and struct mirrors. Keep it free of Lisp conveniences.
  - Each interface function is kept in a variable named after the C function (`*string-name-new-with-latin1-chars*`), and called through a Lisp function with the same name without earmuffs. The variable is set in `load-interface`.
  - Function pointers returned by Godot (constructors, operator evaluators) are called with `call-*` functions. Those looked up once for every type, such as the destructors and the Variant constructors, are cached in `load-interface` too.
  - It also has the helpers for ECL's foreign memory (`cast-pointer`, `foreign-ref`, `clear-foreign-object`), since every layer needs them.
- `gd-extension-types` (`lisp/gd-extension-types.lisp`, uses `gd-extension-ffi`) has Godot's builtin types in Lisp, see below. Both layers above it convert values with it.
- `gd-extension-callback` (`lisp/gd-extension-callback.lisp`, uses `gd-extension-ffi` and `gd-extension-types`) is what runs when Godot calls into Lisp: all the callbacks (`ffi:defcallback`), and the tables and dispatchers behind them (the method dispatcher, and the class and instance tables). The callbacks themselves only convert between C and Lisp, catch errors and call the dispatchers.
- `gd-extension` (`lisp/gd-extension.lisp`, uses `gd-extension-ffi` and `gd-extension-types`, and imports from `gd-extension-callback`) is the public, Lisp-style layer: initialization and hooks, `with-` macros, and registering classes, methods, properties and signals. It fills in Godot's info structs with the callbacks' addresses (`(ffi:callback 'name)`) and adds entries to `gd-extension-callback`'s tables. It re-exports what applications need from the layers below, such as `cast-pointer` and `instance-object`.
- The dependencies only go downwards; keep it that way.
- Don't look anything up in Godot at load time, only in `load-interface`/`initialize` or later. ASDF loads the framework into the build image to compile what depends on it, and there's no Godot there.

## FFI notes

- Interface functions are looked up with `get-proc-address` and called with `si:call-cfun`. Godot structs are mirrored with `ffi:def-struct`. Sizes such as `+string-name-size+` come from `builtin_class_sizes` in `extension_api.json`, build configuration `float_64`. Check new struct mirrors against C with `sizeof`/`offsetof`.
- A `:pointer-void` returned by a foreign function has no size in ECL, so its slots can't be accessed until it's cast: use `cast-pointer`, or `foreign-ref` for `((TYPE *)p)[i]`.
- Godot → Lisp callbacks use `ffi:defcallback`, and `(ffi:callback 'name)` gives the C function pointer. `defcallback` accepts fewer types than `si:call-cfun`: `:uint8-t` is rejected, so declare `GDExtensionBool` as `:unsigned-byte`.
- Wrap every callback body in `handler-case`. A Lisp error must never unwind through Godot's C frames. Report it with `report-error`, which uses Godot's `print_error` (so it shows in the editor's Output and Debugger) with where it happened, e.g. the method name, and can't fail itself. A bound method that fails returns null with `CALL_OK`, like a failing GDScript method; there's no call error for it, and `CALL_ERROR_INVALID_METHOD` would make Godot say that the method doesn't exist.
- With `ptrcall`, an `Object` argument is passed as a pointer to the object pointer, and every argument must be given, including those with default values.
- Method binds need the method's hash from `extension_api.json`. `classdb_get_method_bind` returns NULL if the hash doesn't match; `lookup-method-bind` then signals an error, which `initialize` reports with `report-error` (so it shows in the editor), and the engine method signals an error when it's called.

## Variant types

Applications give types (bound methods' arguments and results, properties, signals, `:extra-arguments`) as variant type designators, resolved by `variant-type` in `gd-extension`: a keyword named like a `+variant-type-…+` constant of `gd-extension-ffi` (`:int`, `:vector2`, `:packed-string-array`), or the constant itself. The lower layers only take the integers.

`bind-property`'s `:class` sets the property's class name and hint string to the class, and the hint to `PROPERTY_HINT_RESOURCE_TYPE` or `PROPERTY_HINT_NODE_TYPE`, by whether the class inherits from Resource or Node (`inherits-class-p`, with `ClassDB.is_parent_class`, also used by `bind-virtual`), like `@export` with a class type in GDScript.

## Method dispatcher

All methods bound with `bind-method` share one pair of callbacks, `method-call` (Variants) and `method-ptrcall` (raw values). `method_userdata` is an index into `*bound-methods*`, a table of `bound-method` descriptors (function, return type and argument types, see `register-method`). `register-method` looks up the `value-type` of each argument and the return value once (see Builtin types), and the dispatcher converts with them. It handles the types with a raw value that can also be a Variant: currently `bool`, `int`, `float`, Vector2, Rect2, String and Object (the object pointer, or the Lisp object of an instance, see Classes; in a ptrcall, Godot passes a pointer to it). Bound functions get the instance's Lisp object (`instance-object`), like `self` in GDScript. In a Variant call, the raw values it makes from Variants (arguments) or for a Variant (the result) are temporary, and destroyed afterwards if their value type has a destructor (String). In a Variant call, an Object argument also accepts Nil (GDScript's `null`), as `nil`, and an int argument a float (truncated, like `int()`) and a float argument an int, as Godot converts them for its own methods.

## Classes

`register-class` registers an extension class with `classdb_register_extension_class4`. All classes share the callbacks `create-instance` and `free-instance`; `class_userdata` is an index into `*extension-classes*` (see `add-extension-class`). `create-instance` constructs an object of the parent class with `classdb_construct_object` and makes it an instance of the extension class with `object_set_instance`. The class's constructor makes the instance's Lisp object, kept in `*instances*` so the GC can reach it; the `GDExtensionClassInstancePtr` is an index into that table (`instance-object`). `*lisp-objects*` maps the address of each instance's Godot object to its Lisp object (`lisp-object`), kept up to date in `add-instance` and `remove-instance`. Lisp objects are `godot-object`s (`gd-extension-types`), or structs that include it, with the Godot object pointer in the slot `pointer`; the default constructor makes a plain one. `nil` is Godot's null: `object-pointer` makes it a NULL pointer, and `read-lisp-object` reads a NULL pointer as `nil`. Everything that passes an Object to Godot takes a `godot-object` or a pointer, through `object-pointer` (inline): `write-object`, the object an engine method is called on, references, Callable targets. In the other direction, `gd-extension-callback` replaces the Object value type's reader with `read-lisp-object` (`add-value-type`, as for Callable), which gives the Lisp object of an instance, and otherwise the pointer: for engine method results, bound method arguments and Variants. That's a hash lookup per Object read; Objects that aren't instances stay pointers, with no wrapper (see the CLOS notes for engine objects). Virtual methods (`bind-virtual`) use `get_virtual_call_data_func` and `call_virtual_with_data_func`, not `get_virtual_func`. A virtual method is registered like a bound method (`register-method`), and its `method_userdata` is the call data; Godot calls it with raw values, as with `ptrcall`, so `call-virtual-with-data` uses `ptrcall-bound-method`. `get-virtual-call-data` compares the name with each of the class's virtuals with Godot's StringName `==` (`*string-name-equal-evaluator*`), and returns NULL for virtuals the class doesn't implement, so Godot doesn't call into Lisp for them. Godot asks once per object and virtual method, the first time it would call it. `bind-virtual` is a macro: the virtual method's signature is looked up in `extension_api.json` when it's expanded (`api-virtual-methods`, `virtual-signatures`). Engine classes can have virtuals with the same name and different signatures (`_process` is in Node, AnimationNode, MainLoop, …), and the extension class's parent isn't known at expansion, so the expansion has the signatures of all of them, and `bind-virtual-with-signatures` picks the one of the class the extension class inherits from with `ClassDB.is_parent_class`, once, at registration. A signature with types that can't be mapped to variant types is kept with the reason, and is an error only if it's the one picked.

`define-class` defines a class in one form: a `defstruct` that includes `godot-object`, and a registration function (`register-class`, then `bind-property` with generated `get_`/`set_` methods for `:export` slots, then the `:signal`, `:method` and `:virtual` options) given to `add-class-definition`. `register-defined-classes`, an initialize hook added when `gd-extension` is loaded (so before the application's hooks), runs them in definition order, each in its own `handler-case`; after `initialize` (at a REPL) `add-class-definition` runs it right away. Functions given as symbols are stored as symbols, so redefining them takes effect. An `:export` slot with a `:class` and no `:setter` manages references: whether the class is RefCounted is found out once, in the registration function (`inherits-class-p`), into a variable that the generated setter (`setf-reference`) and the generated destructor (which releases the slot's value after the application's `:destructor`) close over. With a `:setter`, references are up to the application. `:onready` slots are set by a generated `_ready` (with `node-get-node`, an engine method of `gd-extension`'s own, for a path, or by calling the function), which then calls the class's own `(:virtual "_ready" …)`, if any: the option is replaced, not bound twice. Godot can't register the same class twice, so redefining a class at a REPL doesn't work yet.

## Builtin types and engine methods

- `gd-extension-types` has Lisp structs for Godot's builtin types (`vector2`, `rect2`), with `read-` and `write-` functions for raw values and `write-variant`; `gd-extension` and `godot` re-export what applications use (the same symbols, so a package can use both). Their functions are named like engine methods, `<type>-<method>` (`vector2-normalized`).
- `*value-types*` in `gd-extension-types` is the one table of how each type converts between raw values and Lisp values (`value-type`: FFI type, reader, writer, destructor; `find-value-type`). Both the method dispatcher and `define-engine-method` use it; add a type there. The readers and writers take untyped pointers, as Godot passes them, and cast them themselves. StringName and NodePath have no FFI type: they're passed as the pointer to them. `:variant` stands for any Variant. The FFI mirrors of the raw values are named `godot-vector2` and `godot-rect2`, like `godot-string`, so the plain names are free for the Lisp types. Their layouts come from `builtin_class_member_offsets` in `extension_api.json` (`float_64`: `real_t` is `float`).
- Things looked up in Godot once, such as method binds, StringNames (`sname`), NodePaths (`npath`) and singletons (`singleton`), are kept in initialize cells (`make-initialize-cell`, in `gd-extension-callback`): a cons whose car `initialize` computes before running the initialize hooks (or `make-initialize-cell` right away, if `initialize` has run, e.g. at a REPL). Code gets the cons with `load-time-value`, so there is no lookup per call, and nothing is looked up at load time.
- `define-engine-method` expands into a `defun` that calls a Godot method with `object_method_bind_ptrcall`, with its method bind in an initialize cell. The generated code converts each argument and the result with the readers and writers in `*value-types*`, called directly, and destroys raw values that have a destructor after the call. The return slot is zeroed before a ptrcall: Godot assigns the result into it (e.g. `Ref<T>` and `PackedStringArray` assignment), which releases the old value first.
- A RefCounted result comes with a reference the caller owns (Godot encodes it as a `Ref<T>` in the return slot); `add-reference` takes a reference (`RefCounted.reference()`), for RefCounted objects Lisp keeps, e.g. in a property's slot; `release-reference` gives one back with `RefCounted.unreference()` and `object_destroy`s the object if that was the last one, and `with-reference` does it around a body; `setf-reference` sets a place that keeps a reference (`get-setf-expansion`), taking the new reference before giving back the old one, in case they're the same object. Engine methods don't do this themselves yet; `extension_api.json` says which classes are RefCounted (`is_refcounted`), so they could. A Variant argument has the type `:variant` (Godot's variant types have no "any Variant"); it's made from the Lisp value by its Lisp type with `write-variant` (`lisp-variant-type` maps Lisp types to variant types; the raw value is written with that type's writer from `*value-types*`, so a type with a writer there only needs a line in `lisp-variant-type`). A Variant result is read by its type with `read-variant`, the reader of `:variant`. A StringName or NodePath argument is passed as the pointer to it, and an Object as the object pointer. In a ptrcall, a float is always a double and an int an `int64_t`, whatever the `meta` in `extension_api.json`. Arguments with a default value become `&optional`. Vararg methods can't be called with ptrcall. They go through `object_method_bind_call` with every argument converted to a Variant (`variant-call-method-form`), a call error becomes a Lisp error, and the Variants are destroyed afterwards. The Variant array is zeroed (all Nil) before the arguments are converted inside the `unwind-protect`, so it can always be destroyed whole. Their functions take `&rest arguments` after the declared ones, converted with `write-variant`, so the arrays' sizes are computed at runtime; or `:extra-arguments` declares them with their types, as in `variant-type`, and then there's no `&rest`.
- `define-engine-method` takes only the class and method name. The method's hash, argument names and types, return type, default values and whether it's vararg or static are looked up in `extension_api.json` when the macro is expanded (`lisp/extension-api.lisp`), also in the classes the class inherits from; the method bind is looked up with the class that defines it. `extension_api.json` is read once per build, with gdecl's own JSON reader, `gdecl-json` (about half a second; objects become alists), from the path of the source file when it was compiled, so nothing is read at runtime. Its type names are mapped to variant types by `*variant-type-names*` (`builtin_classes` isn't in variant-type order: it has no Object), enums and bitfields to int, engine classes to Object and `Variant` to `:variant`; a type the engine methods can't convert is an error at expansion. Only the last arguments with defaults `api-default-form` can express in Lisp become optional (bool, int, float, String, `&"..."` as `sname`, `NodePath("...")` as `npath`, Vector2 and `null`, as `nil`). Argument names are interned in the current package in Lisp style. A static method's function has no object argument, and neither has that of a method whose defining class is an engine singleton's class (`api-singleton`, from `singletons` in `extension_api.json`; their names are the classes' names): it's called on the singleton, from `(singleton name)`. Methods a singleton inherits (from Object) still take the object.
- For a method with StringName or NodePath arguments, `define-engine-method` also defines a compiler macro that wraps a literal string given for one of them in `sname` or `npath` (`wrap-literal-names`), so applications can write `(emit-signal object "hit")` without a per-call cost. Only literal strings are wrapped. A Lisp string at runtime becomes a temporary StringName (UTF-8, `string_name_new_with_utf8_chars`) or NodePath for the call (`temporary-names-form`, `make-temporary-name`), destroyed afterwards in an `unwind-protect`; the call form isn't duplicated, so a pointer costs only the `stringp` check. Compiler macros don't apply to `funcall`/`apply` with a function object, or to calls compiled before the definition.
- Calls allocate a little (the argument list of `si:call-cfun`, and Lisp structs for Vector2 results). Measure before optimizing.
- Enums and constants are `defconstant`s in `godot`, named `+<name>+` in Lisp style (`constant-defconstant`): `define-global-enums` defines the values of the global enums (`global_enums`, 22 enums and 509 values; their names are unique and carry their enum's prefix, `KEY_ESCAPE`), and `define-engine-class` the values of the class's enums and its constants with the class's prefix (`+node-process-mode-always+`, `+node-notification-ready+`), only for the classes defined, not all 4,600. `gd-extension` keeps its own `+connect-one-shot+` for `after-signal`, since it can't depend on `godot`.
- `define-utility-functions` defines a function in `godot-utility` for each of the utility functions in `extension_api.json` (`utility_functions`: @GlobalScope's `randf_range`, `push_error`, `lerpf`, …), with `utility-function-defun`, which generates the same code as engine methods (`ptrcall-method-form` and `variant-call-method-form` with `:utility t`): a function pointer from `variant_get_ptr_utility_function` in an initialize cell, called with raw values, or, for vararg ones, with Variants, but the result of a vararg one is a raw value of its return type, not a Variant. Names that are Common Lisp symbols (`sin`, `abs`, `min`, …, 20 of them) are skipped, since `godot-utility` uses `cl`, and Lisp's are as good and cheaper; `print` is `godot-print`. Functions with unsupported types are skipped as for engine classes (6 now). 88 functions: about 12 s of build time and 2 MB.
- `define-engine-class` defines `<class>-<method>` (`lisp-style-class-name`, `lisp-style-method-name`: `Node2D` is `node-2d`, `HTTPRequest` `http-request`) for each method the class itself defines (not inherited ones, so each method has one name), with `engine-method-defun`; methods it signals an error for (unsupported types, Variant results) and virtual methods are skipped, so the set grows as types are added. The functions, and their arguments' names, are always interned in `godot` (`*package*` is bound while expanding) and exported from it, also for classes an application defines, so all of Godot's API is in one package. Every method is a compiled function with its own conversion code: measured, about 70 ms of build time and 15 KB of library per method (the ~360 functions of `godot` take about 25 s to compile and 5.5 MB). ASDF only recompiles changed files, so it costs only when gdecl changes. If it grows too much, the per-method code could call shared conversion functions instead of being expanded inline, or the class list in `godot-engine-classes.lisp` could shrink.
- `register-class` makes runtime classes (`is_runtime`) unless given `:tool t`: in the editor, instances are placeholders that keep their properties but run no code, like GDScript without `@tool`.

## Callables and signals

- A Lisp `callable` (`gd-extension-types`: a target object and a function) becomes a custom Godot Callable with `callable_custom_create2` (`write-callable` in `gd-extension-callback`, which adds the Callable value type to `*value-types*` with `add-value-type`, since the types layer can't refer to the callbacks above it). All custom Callables share the callbacks `callable-call` and `callable-free`; `callable_userdata` is an index into `*callables*`, the table of Lisp functions, and `callable-free` forgets the function when Godot frees the last copy of the Callable.
- `object_id` is the target's instance ID. Godot doesn't call a Callable whose object is gone (and skips signal connections without an object), so it must be set. `token` is the class library.
- `callable-call` converts the arguments with `read-variant`, by each Variant's type, and returns the function's result as a Variant (`write-variant`) if `variant-value-p`; `nil`, and values that can't be Variants yet, return null, not an error, since Callables are mostly signal handlers whose results Godot ignores. Godot doesn't initialize `r_error` for custom Callables (unlike for method calls), so `callable-call` sets it to OK.
- `connect-signal` connects a signal to a Lisp function with `Object.connect`, and `after-signal` connects a body with `CONNECT_ONE_SHOT`, for GDScript's `await`: the code after the await becomes the body of a closure. `connect-signal` has a compiler macro like the engine methods' (`wrap-literal-names`) for a literal signal name; `after-signal` expands into a call of it with the signal-name form as given, so it gets it too.
