# gdecl

Guidance for working on the gdecl framework: Godot 4 GDExtension programming in Common Lisp with ECL, without godot-cpp. User-facing documentation is in `README.md`; what each function does is in its docstring; known gaps and planned work are in `TODO.md`. This is its own repository (github.com/flambard/gdecl), used by applications as a git submodule, so keep it free of anything specific to an application.

## Goal and direction

GDExtension is a low-level C interface, not meant to be used directly by application developers. gdecl's goal is to raise the level of abstraction step by step until writing a Godot application in Lisp is at least as easy as with GDScript or C#, while staying efficient. Godot is mostly used for games, which are performance sensitive, so ease of use must not cost per-frame overhead.

Principles:

- **Build up gradually.** Each layer is built on the ones below it (see Layers), with the highest-level concepts on top of `gd-extension`: `godot-clos`, the high-level layer, and `godot-dsl` (`define-class`), a faster, lower one (see The high-level layer below). Grow the framework from what the applications built on it need, and move code from an application into gdecl once the pattern is clear.
- **High level by default, drop down where it matters.** Applications should be able to program at a very high level, and drop down to lower-level concepts exactly where a task is performance sensitive, without giving up the high level elsewhere: one method of a high-level class, or one hot loop, can use a lower layer. So the layers must work together: high-level objects can be passed to everything below (as `godot-object`s are through `object-pointer`), a high-level class can have methods bound the low-level way, and the lower layers stay usable and documented. Speed is opt-in step by step: type declarations, non-allocating operations, dispatch resolved once.
- **Performance first: shift work from run time to compile time.** gdecl is for games, so every design is judged by what it costs per frame. Do at compile time (macros, code generated from `extension_api.json`) what can be done then, and at initialization or registration what has to wait for Godot (method binds, StringNames, constructors, cached once); keep only what must happen per call at run time. Prefer `ptrcall` to Variant calls, avoid allocating in calls that happen every frame (`_process`, `_physics_process`), and prefer deterministic, explicit resource handling (such as the autorelease pool, decided per method when the code is generated) to run-time machinery such as GC finalizers. See Performance in ECL for what that means in practice.
- **Improve gdecl as you go.** When an application needs something gdecl lacks, or something in it could be better, improve gdecl rather than working around it in the application. Keep such changes general.
- **Measure.** Before choosing a convenient but slower design for something called often, check what it costs (see Benchmarks).
- **High cohesion, a consistent style and consistent names.** They make the codebase easier to understand and to work with.
  - **One place per concern.** Keep each concern in one place, and each file about one concern, with a header comment that says what's in it and where the related code is. Examples: `*value-types*` is the one table of how each type converts, `handle-tables.lisp` the one implementation of the tables behind the callbacks, and `lifecycle.lisp` the one place for the framework's startup and shutdown order.
  - **Don't copy knowledge.** When the same code, or the same knowledge about a type, is about to appear in a second place, move it into one instead. Code that only works because of the order files load in is a sign it belongs somewhere else.
  - **No knowledge from a layer above.** A lower layer gets what it needs from a higher one through a hook the higher layer sets, as `literal-macro` and `*release-reference-function*` do.
  - **Write like the code around it:** the same idioms, and docstrings and comments filled to 80 columns.
  - **One name for one concept**, used everywhere:
    - `look-up-…` for the verb.
    - "binding" only for instance bindings; registering classes, methods, properties and signals is "registration".
    - `godot-<type>` for FFI mirrors, and `read-`/`write-` for converters.
  - **Rename when a name stops fitting** what the code does, everywhere, docs and TODO.md included.
  - **Performance comes first.** When the cohesive form costs time on a per-call path, as a struct around the handle tables did, measure, keep the fast form, and say why in a comment.

Where to look for inspiration:

- **GDScript**: the API application developers know: `extends`, `@export`, `signal`, virtual methods such as `_ready` that you just define, `$Node` paths, `@onready`.
- **Godot C# (`GodotSharp`)**: the closest model, a garbage-collected binding. Engine classes are generated from `extension_api.json` with method binds cached in static fields, builtin types such as `Vector2` are implemented in C#, user classes use attributes and a source generator writes the registration code, and `RefCounted` lifetimes are tied to the managed object.

### The high-level layer: CLOS, with a fast path (decided, TODO P)

The ambition is to program Godot at a high level in Lisp: Godot's object-oriented concepts (classes and inheritance, virtual methods, properties, signals) expressed naturally, at least as easy as GDScript and C#, and fast enough for games.

Decided on 2026-10-17: CLOS, `godot-clos`, is the high-level layer. A class is a `defclass` with the metaclass `godot-class`, and what Godot calls are generic functions, so classes get inheritance, mixins, method combination (e.g. `:before` methods on `_ready`) and redefinition in a running game (`update-instance-for-redefined-class`), which is probably Lisp's strongest selling point here. `define-class` (`godot-dsl`) stays as a faster, lower layer, a struct and functions called by name, for dropping down, but gets no new high-level features: inheritance between Lisp classes, redefinition at a REPL and the rest of GDScript go into `godot-clos`.

Why: a call from Godot into a generic function costs 0.53–0.54 µs, against 0.35–0.39 µs into a `define-class` function, and an accessor 80 ns against 25 ns for a struct accessor. That's about 0.2 ms a frame for 1,000 objects with `_process`, about 1%, and small next to what entering Lisp costs at all (N in `TODO.md`, now at its floor), which both pay. CLOS's dispatch can't be made cheaper by resolving it once (see below), so where a class's hot code needs `define-class`'s speed, it drops down: a hot virtual method bound to a plain function with `:direct-functions`, which costs what `define-class` does (an empty `_process`, called through `NOTIFICATION_PROCESS`: 0.32–0.35 µs, against 0.44–0.45 µs through the generic function), and, for slot access, hot data kept in a struct that the object holds in one slot, so that hot code pays for one generic accessor and uses struct accessors from there (see the README; faster CLOS accessors are TODO AM).

What `godot-clos` rests on:

- **A CLOS class can inherit from structs** in ECL, when `validate-superclass` allows it: a `godot-class` inherits from the struct of its engine class, so its instances are `godot-object`s to every layer below, with no change to them. The structs' slots come first, so `pointer` is at location 0 (`+godot-object-pointer-location+`, which `types` checks against the struct when it's loaded), where the structs' accessors read it, provided mixins come before the struct in the superclasses (checked when the class is finalized). `standard-object` is added to the superclasses, since redefinition needs its methods.
- **ECL gives fast slot access only to `standard-class`** (see Performance in ECL), so `godot-class` sets up the location table and optimized accessors itself.
- **Dispatch isn't resolved once.** ECL's method functions take their arguments as a list, so calling an effective method computed once is no faster than the generic function (measured: 137 ns against 160 ns, and it conses).

Open questions: generated classes for engine classes, and only for those used, instead of the structs of `define-engine-class`; RefCounted lifetimes tied to their Lisp objects (finalizers), now that every Godot object has one Lisp object.

## Layers

From the bottom up; dependencies only go downwards. Each layer is a directory of `lisp/`, with its packages in its own `package.lisp`, and a module in `gdecl.asd` whose `:depends-on` names the layers it uses. A package is defined only once the layers below it are loaded, so code in a lower layer can't even read a symbol of a higher one.

| Directory | Package | |
|---|---|---|
| `extension-api/` | `gdecl-json`, `extension-api-json` | `extension_api.json`, read with a small JSON reader when the code is compiled |
| `ffi/` | `gd-extension-ffi` | The GDExtension C interface |
| `types/` | `gd-extension-builtins`, `gd-extension-types` | Godot's builtin types in plain Lisp, foreign memory for Godot's opaque values, and converting values between Godot and Lisp |
| `callback/` | `gd-extension-callback` | What Godot calls into |
| `gd-extension/` | `gd-extension` | The public, Lisp-style layer, and the code generators |
| `godot/` | `godot`, `godot-utility` | Godot's API, generated |
| `dsl/` | `godot-dsl` | `define-class`, a small DSL: a class in one form, with a struct for its instances; faster and lower-level than `godot-clos` |
| `clos/` | `godot-clos` | The high-level layer: classes as CLOS classes |

The layers load in this order, each after those it uses (an arrow from A to B means A uses B). `ffi` and `extension-api` depend on nothing in gdecl:

```
   dsl/     clos/
      \      /
      godot/
        │
   gd-extension/
        │
     callback/
        │
      types/
      /     \
   ffi/   extension-api/
```

Many layers also use layers further down directly: `gd-extension` uses all the layers below it, `godot` uses `types` (for the builtin types), `callback` uses `ffi`, and `dsl` and `clos` use `gd-extension`. The class layers, `dsl` and `clos`, use only the public layers, `gd-extension` and `godot`: what they need from further down, `gd-extension` exports (`report-error`, `invoker-form`, `godot-object` and where its pointer is, `+godot-object-pointer-slot+` and `+godot-object-pointer-location+`), so the layers below can change behind it. Each module's `:depends-on` in `gdecl.asd` lists exactly the layers its code uses (in `:use`, `:import-from` and package-qualified symbols), shortcuts included, so keep it in step when a layer starts or stops using another.

- `extension-api-json` (`extension-api/extension-api.lisp`): `extension_api.json`, the one place that knows the file: where it is (`*extension-api-file*`), reading it once with gdecl's own small JSON reader (the function `extension-api-json`; the package `gdecl-json`, `extension-api/json.lisp`), and looking things up in it when the code is compiled: the sizes of the builtin types (`api-builtin-size`), constants (`api-constant`), and the engine classes, methods, enums and utility functions that the code generators of `gd-extension` use. That the API comes from a JSON file is its own business: it reads the parts the layers above use into Lisp structs (`api-class`, `api-method` for methods and utility functions alike, `api-argument`, `api-enum`; enum values and constants as `(name . value)`), and its lookups return those, so JSON stays in `extension-api/`. Types keep Godot's names (`"Vector2"`, `"enum::Node.ProcessMode"`). Building the structs adds about 40 ms to the half second that reading the file takes. When a generator needs more of the API, add it to the structs and their readers (`read-api-class` etc.) rather than reading JSON elsewhere.
- `gd-extension-ffi` (`ffi/`): the GDExtension C interface, one-to-one, without Lisp conveniences. Each interface function is a variable named after the C function (`*string-name-new-with-utf8-chars*` for `string_name_new_with_utf8_chars`), set in `load-interface`, and a wrapper function of the same name without earmuffs. Also ECL foreign-memory helpers (see Performance in ECL). It depends on nothing else in gdecl: the sizes of Godot's opaque values, which only `extension_api.json` has, are in `types` (`opaque-values.lisp`).
- `gd-extension-builtins` (`types/builtin-types.lisp`): Godot's builtin types (`vector2`, `basis`, …) in plain Lisp. Everything it exports is for applications: `godot` re-exports all of it through an export list computed when its package is read (`godot/package.lisp`), so a new symbol is exported in one place only.
- `gd-extension-types` (`types/`): converting between raw values, Lisp values and Variants.
  - `*value-types*` (by variant type) is the one table of how each type converts, and the code generators look types up there instead of knowing them. A value type has its FFI type (the C type follows from it, `c-type-name`) and its readers and writers, and optionally:
    - `to-raw`/`from-raw`, form generators for simple types, whose raw value is a C number or pointer, so they're converted in C (`define-simple-value-type`: bool, int, float, Object);
    - `by-pointer` for StringName and NodePath, which engine methods take as a pointer, with `literal-macro` (`sname`, `npath`, set by `gd-extension`);
    - a `default-parser` for default values in `extension_api.json`;
    - `lisp-type`, the type specifier `write-variant` uses to find the variant type of a value (`lisp-variant-type`): a struct such as `vector2`, `hash-table`, or a vector type.
  - In files of their own: foreign memory for Godot's values whose layout is opaque to GDExtension, the structs `variant`, `string-name`, `godot-string`, `packed-array` etc. and their sizes, such as `+variant-size+`, from `extension_api.json` (`opaque-values.lisp`); Strings, StringNames and NodePaths (`strings.lisp`: creating, reading and destroying them; `gd-extension.lisp` keeps only the cached `sname` and `npath`), and the autorelease pool (`autorelease-pool.lisp`).
- `gd-extension-callback` (`callback/`): everything Godot calls into, and the tables behind the callbacks, in files loaded in this order: `gd-extension-callback.lisp` (`define-callback`, threads, `with-callback-protection`), `handle-tables.lisp` (the tables of the Lisp values Godot holds handles to), `initialize.lisp` (`initialize` and `deinitialize`, called from `src/gdecl.c`, their hooks, and initialize cells), `instance-bindings.lisp` (`lisp-object`, the Object value type), `extension-classes.lisp` (classes, instances, which virtuals a class implements, notifications), `bound-methods.lisp` (methods and virtual methods, invokers, `call-virtual-with-data`) and `callables.lisp` (Callables in both directions, see Callables in Rules and pitfalls).
- `gd-extension` (`gd-extension/`): the public, Lisp-style layer, in several files (see the header of `gd-extension.lisp`). `api-types.lisp` turns the types of `extension_api.json` into variant types for the code generators, and signals `unsupported-api-type` for those gdecl can't convert yet; it's here rather than in `extension-api/` because it needs the variant types of `gd-extension-ffi`.
- `godot` and `godot-utility` (`godot/`): Godot's API generated from `extension_api.json` (`define-engine-class`, `define-global-enums`, `define-utility-functions`). Applications add the engine classes they use to `godot`.
- `godot-dsl` (`dsl/`): `define-class` (`define-class.lisp`), which expands into the registration functions of `gd-extension` and a struct that includes the engine class's. A faster, lower layer than `godot-clos`, for dropping down; it gets no new high-level features (see The high-level layer). It uses a few internals of `gd-extension`, listed in its `:import-from` clauses.
- `godot-clos` (`clos/`): the high-level layer (see The high-level layer), classes as CLOS classes: the metaclass `godot-class` (`godot-class.lisp`), the generic functions Godot calls, virtual methods, methods and `notification` (`godot-functions.lisp`), and registering the classes (`godot-registration.lisp`). It uses a few internals of `gd-extension`, listed in its `:import-from` clauses.

Consequences of the layering that aren't obvious:

- The types layer can't refer to the callback layer, so `gd-extension-callback` adds the value types of Object (whose Lisp values are the objects' Lisp objects) and Callable.
- Releasing a reference needs an engine method, so `gd-extension` sets `*release-reference-function*` for the autorelease pool in the types layer; likewise the `literal-macro` of StringName and NodePath.
- `gd-extension` can't depend on `godot`, so it defines the few engine methods it needs itself, and its own few constants, such as `+connect-one-shot+`, with `api-constant`.
- The code generators in `gd-extension` (`define-engine-class`, `define-global-enums`, `define-utility-functions`) define and export their functions in the packages of `godot`, but only when `godot` (or an application) expands them; `gd-extension` never expands them itself, so it doesn't depend on `godot`.
- `dsl` and `clos` give each class's registration to `add-class-definition` in `gd-extension` (`registration.lisp`), and `register-defined-classes`, a step of the framework's startup, registers the classes in the order they were defined.

## Startup and shutdown

- `src/gdecl.c` boots ECL at `GDEXTENSION_INITIALIZATION_SCENE`, with ECL's signal trapping (SIGSEGV etc.) disabled so it doesn't fight Godot's handlers. Loading the Lisp code runs the application's top-level forms, which register its entry point with `add-initialize-hook`. The C side then calls `gd-extension-callback:initialize`, the only Lisp function it knows, which loads the interface, fills in the initialize cells, runs the framework's own startup steps (`*framework-initialize*`: registering the classes that `define-class` and `godot-clos` defined, in the order they were defined, from `add-class-definition` in `registration.lisp`), then the application's initialize hooks.
- At deinit, `deinitialize` runs the application's deinitialize hooks in reverse order while Godot can still be called, then the framework's own shutdown steps (`*framework-deinitialize*`), then ECL is shut down. The framework's steps and their order are set in one place, `lifecycle.lisp`, which says why each comes where it does: `unregister-singletons` (frees the singletons' instances while their classes are still there), `unregister-classes` (subclasses first), `destroy-permanent-values` (the StringNames and NodePaths from `sname`, `npath` and class names), and `free-bindings` last. With them, Godot reports no leaks at exit; the one orphan `Node` the editor reports is Godot's own.

## Adding things

- **A builtin type** (Color, Transform2D, …) takes three things, all in `types/`: the struct, with a constructor that converts its components (Godot's `real_t` is single-float, but Lisp code computes with doubles), and its functions in `builtin-types.lisp`; their exports from `gd-extension-builtins` in `package.lisp`; and a `define-builtin-type` form in `gd-extension-types.lisp`, which generates the FFI mirror of Godot's layout, `read-`/`write-`, exports them, and adds the value type. Defaults such as `Vector2(0, 0)` in `extension_api.json` then work too, for types whose components are all floats.
- **Another type** gets a value type with `add-value-type`, or `define-simple-value-type` if its raw value is a C number or pointer, in the lowest layer that has what its conversion needs (as `containers.lisp` does for Arrays and Dictionaries). Give it a `lisp-type` if `write-variant` should make Variants of it, and a `default-parser` if engine methods' arguments of it have defaults.
- **A file** goes into the directory of its layer, and into that layer's module in `gdecl.asd`. If it needs a layer above, it belongs in that layer, or gets what it needs through a hook (see No knowledge from a layer above). **A layer** is a directory with its `package.lisp`, and a module in `gdecl.asd` that depends on the layers it uses.
- **A framework startup or shutdown step** goes into `lifecycle.lisp`, in the right place in the order, not into `add-initialize-hook` or `add-deinitialize-hook`, which are for applications.
- **An engine method that `gd-extension` itself needs** is defined with `define-engine-method` next to its use (as `class-db-is-parent-class` in `registration.lisp`), since `gd-extension` can't use `godot`.

## Performance in ECL

The measured costs behind the code's design; check them with `make bench` (see Benchmarks) before relying on new ones.

- **Calls between files go through the symbol**, about 50 ns each, so on per-call paths a few small calls add up. Declare small helpers `inline` (as `find-value-type`, `instance-object`, `set-call-error`), and keep lookups a plain `aref` of a variable: reading the vector out of a struct first cost 10–30 ns a call (the handle tables' lookups are macros for that reason, `handle-tables.lisp`).
- **An `inline` function with `&key` arguments is slower than not inlining it**, as ECL's inlined code parses the keywords at run time (measured: 50 ns on a Lisp signal handler). Use `&optional` arguments for inline functions.
- **Keep closures out of per-call code**, even on a rare path inside it: a `lambda` for reporting release errors in `with-callback-protection`, made only when the autorelease pool wasn't empty, slowed every callback by 10–60 ns (measured), most likely because ECL boxes the variables a closure captures.
- **`handler-bind` (and so `handler-case`) conses a handler cluster at every entry**, about 250 ns. `catching-errors` replaces it on per-call paths: it binds ECL's internal `si:*handler-clusters*` to a cluster made once, and exits with `catch`. The cons that puts that cluster in front of those already there is kept and reused while they're the same (`handler-clusters-with`), so a callback allocates nothing for it: measured, `with-callback-protection` around nothing 38–39 ns and no bytes, against 50–53 ns and 16 bytes with a new cons. `with-callback-protection`, around every callback, is built on it; it needs no `unwind-protect`, since nothing but an error can leave a callback.
- **ECL's FFI does at runtime what can be done at compile time, and it's slow** (measured: `get-slot-value` about 5 µs, the size of a struct type about 4 µs, `si:call-cfun` 0.6 µs, `with-foreign-object` 0.6 µs plus the size). On per-call paths, use gdecl's replacements, which generate C code with `ffi:c-inline`:
  - `call-foreign-pointer` (and `define-interface-function`) instead of `si:call-cfun`;
  - `with-foreign-memory` instead of `ffi:with-foreign-object(s)`;
  - `set-foreign-slots` instead of `(setf (ffi:get-slot-value …))`; it also works on pointers without a size;
  - `foreign-ref`, `clear-foreign-object` and `array-element` with a constant type, which compiler macros turn into C. Compiler macros only apply in files other than the one defining the function, so not inside `gd-extension-ffi.lisp`.
  - Avoid `get-slot-value`, `element-pointer`, `cast-pointer` and `size-of-foreign-type` there; registration code can use them.
- **Engine calls in one piece of C.** Engine methods whose types are all simple (bool, int, float, Object, StringName and NodePath arguments, and builtin types made of floats, about 80% of them) are called in one `c-inline` with C variables for the raw values and the argument array (`inline-ptrcall-form`), so they allocate nothing but the result's Lisp value. Vararg methods called with arguments of known types, such as those given with `:extra-arguments`, are called likewise when their types are simple and their result is none, bool, int or float (`inline-variant-call-form`): the Variants are made from the raw values on the C stack and destroyed there (`emit_signal` with an int 0.16 µs, allocating nothing). Other ptrcalls go through foreign memory (`general-ptrcall-method-form`): a `malloc` and a Lisp pointer object for each raw value. Other vararg calls (`variant-call-method-form`), such as those with their further arguments as a `&rest` list, keep the argument array, the Variants, the result and the call error in one block, allocated once with `calloc` and handled by its address (`with-variant-call`), and write the further arguments with `write-variant-at`: `emit_signal` with an int 0.27–0.28 µs and 16 bytes, the list (0.78–0.81 µs and 336 bytes with a `malloc` and a pointer object for each). The primitive types' Variants are also converted in one piece of C each (`define-simple-value-type`), and `read-variant` and `write-variant` convert bools, ints and floats themselves, in one piece of C each, without calling `variant-get-type` or a type's reader or writer by name (the macros `read-simple-variant` and `write-simple-variant`, shared with `read-variant-at` and `write-variant-at`, which take the Variant's address as an integer): measured, `read-variant` of an int 42 ns instead of 101–109 ns, `write-variant` of one with its `variant-destroy` 70 ns.
- **The pointers of the per-call callbacks are integers.** `method-ptrcall`, `call-virtual-with-data`, `method-call` and `callable-call` declare their pointer arguments `:uint64-t`, so ECL passes them as fixnums: with `:pointer-void` it makes a pointer object for each (about 22 ns and 32 bytes), and `ffi:pointer-address` costs 30 ns to get a handle's address back out. The handles are looked up with `address-handle-value`, the invokers read simple arguments and write simple results through the addresses in C, and a pointer object is made (`address-pointer`, `argument-pointer`) only for the readers and writers that need one. `callable-call` and `method-call`, which get Variants, read their arguments and write their results with `read-variant-at` and `write-variant-at` (`write-variant-as-at` for a declared type), so bools, ints and floats need no pointer object, and call a function of up to three arguments without making a list to `apply`. Measured against `HEAD` in alternating runs: a call into an empty Lisp method 0.15–0.16 µs instead of 0.28–0.29 µs; a Lisp signal handler 0.65–0.67 µs instead of 0.74–0.77 µs with the integers, and 0.34–0.35 µs instead of 0.58–0.6 µs with `callable-call`'s own fast paths; a Variant call into a Lisp method with a float argument 0.4–0.42 µs instead of 0.6–0.68 µs.
- **Invokers.** Bound and virtual methods whose types are known when the code is compiled (`bind-virtual`, `define-class` with constant types, and `define-godot-generic`) get an invoker generated for their signature (`ptrcall-invoker-form` in `callback`; macros above `gd-extension` get one with `invoker-form`, which takes types as in `variant-type`), so `ptrcall-bound-method` doesn't build an argument list, `apply`, or call converters by name. `bind-method` called with types at runtime, as for `godot-clos`'s properties, gets an invoker made in advance if it has the signature of a getter or a setter (`signature-invoker`, `registration.lisp`: one of each per type, compiled with gdecl, about 0.1 µs faster a call), and uses the generic path otherwise. The user's function is still called by name, so redefining it takes effect.
- **CLOS** (measured standalone, without Godot): a generic function call 90–95 ns (a call by name 30 ns), with dispatch cached per thread for any class; `slot-value` with a constant name 35 ns and an accessor 29 ns (a struct accessor 20 ns, inline less); `make-instance` 2.3–2.9 µs, `si:allocate-raw-instance` 72 ns. A metaclass other than `standard-class` loses the fast slot access, as ECL builds the slots' location table and uses optimized accessor methods only for `standard-class` itself (compared with `eq`): `slot-value` then takes 337 ns and an accessor 426 ns, through `slot-value-using-class`. A metaclass without `slot-value-using-class` methods can set them up itself, as `godot-class` does. Sealed classes (`(:sealedp t)`) get inlined accessors only at `(safety 0)`; at `(safety 1)` ECL 24.5.10 fails to compile them.
- **Per-method code.** Each engine method is a compiled function with its own conversion code: about 55 ms of build time and 10 KB of object code per method (measured with Control's ~130 methods); the game's library is 8.2 MB. Shared callers per signature with small per-method wrappers would be smaller, but would add a call between files to every engine call, a third of a simple one, so per-method code stays; if size becomes a problem, predefine fewer classes.

## Rules and pitfalls

- **Nothing is looked up in Godot at load time.** ASDF loads gdecl into the build image to compile what depends on it, and there's no Godot there. Lookups go into initialize cells (`initialize-cell-value`), filled in by `initialize`, or right away at a REPL. The cells are filled in before the framework's startup steps, so before the classes are registered: a lookup of something the extension registers itself must wait until it's used, as `singleton` does (singletons from `register-singleton`).
- **A Lisp error must never unwind through Godot's C frames.** Wrap every callback body in `with-callback-protection`, which catches errors and reports them with `report-error` (Godot's `print_error`, so it shows in the editor). A bound method that fails returns null with `CALL_OK`, like a failing GDScript method; `CALL_ERROR_INVALID_METHOD` would make Godot say the method doesn't exist. Called with ptrcall (or as a virtual method), it returns its type's default value, such as 0 or `Vector2(0, 0)`, or null for an Object (`write-failed-result`, written only after an error), as Godot doesn't clear the result's memory; a type with a destructor, such as String, keeps the empty value Godot passes.
- **Godot calls into Lisp from any thread.** Define callbacks with `define-callback`, not `ffi:defcallback`, and give Godot `callback-pointer`: it puts a C function in front that imports the thread into ECL the first time (otherwise ECL aborts the process), and releases it when the thread exits (otherwise the next GC aborts). Only the callbacks are thread-safe so far, not the handle tables behind them (TODO R).
- **ECL FFI:**
  - A `:pointer-void` returned by a foreign function, and pointers from `with-foreign-memory` and `c-inline`, have no size, so cast them before accessing slots with `get-slot-value` (`cast-pointer`), or use `foreign-ref` and `set-foreign-slots`.
  - `defcallback` rejects `:uint8-t`, so declare `GDExtensionBool` as `:unsigned-byte`.
  - Check new struct mirrors against C with `sizeof`/`offsetof`. The mirrors of builtin types are checked for you: `define-builtin-type` signals an error when the code is compiled if their components don't add up to the type's size in `extension_api.json`.
  - C code in `c-inline` can't rely on headers, so use `__builtin_memset` and the like.
  - C code in `ffi:clines` belongs to its file: ASDF compiles each file into a library of its own to load into the build image, so another file can't call a C function or use a variable defined there, not even a non-static one. Pass an address through Lisp instead, as `define-callback` does with `enter-lisp-address`.
  - `array-element-type` gives ECL's names for upgraded types, such as `ext:byte8` for `(unsigned-byte 8)`; compare with `upgraded-array-element-type`.
  - `doc/package-ffi-symbols.txt` and `doc/package-si-symbols.txt` list what ECL's `FFI` and `SI` export.
- **Sizes and layouts** come from the `float_64` build configuration in `extension_api.json`: `real_t` is `float`. Don't copy sizes or enum values by hand: use `api-builtin-size` and `api-constant` (`extension-api/extension-api.lisp`), which expand to the value when the code is compiled, in any layer that imports them (`types` and `gd-extension` so far). The FFI mirrors, generated by `define-builtin-type`, are named `godot-vector2` etc., so the plain names are free for the Lisp types.
- **Basis:** Godot stores the rows, but the Lisp `basis` has the columns, as `basis.x` and `Basis(x, y, z)` in GDScript; `read-basis` and `write-basis` transpose.
- **ptrcall:** every argument must be given, defaults too. An Object argument is a pointer to the object pointer. A float is always a double and an int an `int64_t`, whatever the `meta` in `extension_api.json`. Zero the return slot first: Godot assigns into it (`Ref<T>`, `PackedStringArray`), releasing the old value. Vararg methods can't be ptrcalled.
- **One Lisp object per Godot object.** Every Object that Godot gives Lisp is mapped to its Lisp object through Godot's instance bindings (`lisp-object`, `instance-bindings.lisp`):
  - An instance of an extension class maps to the struct its constructor made (the binding is set in `create-class-instance`), any other object to a Lisp object made on first sight (`create-binding`, which calls `*wrapper-function*`): a struct of the type of its class (`engine-objects.lisp`).
  - `define-engine-class` defines a struct per class, which includes that of the nearest class it inherits from that's defined, so they mirror Godot's inheritance and `typep`, `typecase` and `defmethod` work; `define-class` includes the struct of its engine parent class. A new object's type is found by walking Godot's class parents (a table from `extension_api.json`, made when gdecl is compiled) to the nearest class with a struct, cached by the address of the class name's StringName data, which is the same for the same name while the class is registered.
  - Godot calls `free-binding` when it frees the object, which clears the Lisp object's pointer, so `object-pointer` signals an error for it. `free-bindings`, the last step of the framework's shutdown, frees the remaining bindings before ECL shuts down; otherwise Godot would call `free-binding` after it, e.g. for engine singletons.
  - Code that passes an object to Godot must go through `object-pointer` (`singleton` returns a Lisp object too). Raw pointers are still accepted wherever an Object is passed to Godot, for dropping down, but not where a Variant is made from a Lisp value (`lisp-variant-type`): a raw pointer might point to something else, such as a StringName.
- **Arrays and dictionaries are copies** (`containers.lisp`): packed arrays of numbers are specialized Lisp vectors, copied with `memcpy` and no conversion per element; other packed arrays and Arrays are simple vectors, converted element by element; Dictionaries are `equal` hash tables. Their conversions need Godot's builtin methods (`size`, `resize`, `keys`, looked up with `builtin-method`, hashes from `extension_api.json`), so they're added to `*value-types*` from `gd-extension`. Writers take any sequence, so `#()` is the default value of an empty array argument.
- **Unsupported types:** when the code generator meets a type it can't convert yet, it signals `unsupported-api-type`. `define-engine-class`, `define-utility-functions` and `bind-virtual` skip only that condition, so any other error, such as a bug in the generator, stops the build instead of making methods silently disappear.
- **Method hashes** come from `extension_api.json`; `classdb_get_method_bind` returns NULL on a mismatch, which usually means the JSON was dumped from another Godot version.
- **Notifications** go to a class's `notification_func`, which Godot calls for every notification of the object, including some every frame (`NOTIFICATION_PROCESS`), and without the class userdata. So `*instances*` holds each instance's class with its Lisp object, and Godot calls a C function, `gdecl_notification`, that passes on only the notifications some class wants, from a table of flags; the callback then checks the instance's own class. Only classes with a notification function get a `notification_func`. `free_instance` runs from Godot's `Object` destructor, after the engine classes' destructors, so code that cleans up with calls to Godot belongs at `NOTIFICATION_PREDELETE`, not in a destructor.
- **Virtual methods** use `get_virtual_call_data_func`, which returns NULL for those the class doesn't implement, so Godot never calls into Lisp for nothing. Several engine classes have virtuals with the same name but different signatures (`_process`), and the parent class isn't known when `bind-virtual` expands, so the expansion carries all of them and the right one is picked at registration.
- **Godot can't register a class twice**, so evaluating a `define-class` again at a REPL doesn't work yet (TODO J). Functions given to `define-class` as symbols are called by name, so redefining those does. `godot-clos` registers only what's new when a class is redefined (`godot-registration.lisp`).
- **Literal names:** a compiler macro wraps literal strings given for StringName and NodePath arguments in `sname`/`npath`. That doesn't apply through `funcall`/`apply`, to calls compiled before the definition, or to calls in the same file as the definition, as ECL doesn't use a compiler macro in the file that defines it; then each call makes a temporary one (measured: `emit_signal` with `:extra-arguments` 1.7 µs instead of 0.7 µs before AH). So define engine methods with `define-engine-method` in a file of their own, as `test/lisp/engine-classes.lisp` does.
- **Callables:** `object_id` must be set, since Godot skips connections without an object. Godot doesn't initialize `r_error` for custom Callables, so it's always set. A result that can't be a Variant becomes null, not an error, since Godot ignores signal handlers' results. A Callable read from Godot is the `callable` it was made from if it's one of gdecl's own (found with `callable_custom_get_userdata` and gdecl's token, `*class-library*`), so `*callables*` keeps the `callable`, not only its function; any other is an `engine-callable` with a copy of it (`callback/callables.lisp`), which `gd-extension/callables.lisp` calls and compares.
- **Variant calls into bound methods** accept null for an Object, and a float for an int (truncated) or an int for a float, as Godot does for its own methods.

## References (RefCounted ownership)

- An engine method's RefCounted result comes with a reference (a `Ref<T>`). During a call from Godot (every callback, and every initialize/deinitialize hook and framework step) it goes into the autorelease pool and is given back when the call returns. Outside a call, e.g. at a REPL, there's no pool and the caller owns it.
- An Object Variant result: the Variant is copied and the copy is kept until the pool goes, which keeps the reference without having to ask Godot whether the object is RefCounted.
- An Object a bound or virtual method returns with ptrcall needs a reference for Godot (`reference-for-caller`): Godot puts the pointer into a Variant or `Ref<T>` without taking one, and gives one back later. Without it, a typed GDScript call of a RefCounted getter released a reference it never got.
- Arguments never take a reference: the caller owns those Variants.
- The copy of a Godot Callable in an `engine-callable` goes into the pool too (`autorelease-callable`), so a Callable read from Godot is valid until the call returns; destroying it clears the struct's pointer, so using it afterwards signals an error instead of reading freed memory. `keep-callable` makes a copy that isn't in the pool.
- `setf-reference` takes the new reference before giving back the old one, in case they're the same object.
- An exported slot of a RefCounted `:class` owns a reference to its value, given back when Godot frees the instance, so every way gdecl puts a value there takes one: the property's setter (`setf-reference`), the constructor for the values of initforms (in both class layers: an initform's object is made in `create_instance`, whose pool gives back its first reference when the callback returns), `godot-clos`'s `make-instance` for initargs (taking the new values' references, then giving back the replaced ones), and an instance updated after its class is redefined with a new such slot (`godot-registration.lisp`). Writing the slot directly is the application's to handle with `setf-reference`.

## Build

- `gdecl.mk` builds the application's ASDF system monolithically into `$(BUILD_DIR)/application.a`, always with the init function `init_lib_APPLICATION`, which `src/gdecl.c` calls by name; keep the two in sync. `application.a` must come before ECL's flags (`-lecl`) when linking.
- Changing `SYSTEM` doesn't make `application.a` out of date; use `make -B`.
- `src/gdextension_interface.h` and `extension_api.json` are generated by Godot (`make godot-api`) and ignored by git; don't edit them. The `EditorSettings not instantiated yet` error while dumping is harmless.
- Reading `extension_api.json` takes about half a second per build; it's read once (the function `extension-api-json`).

## Tests

- Run `make test` after changing gdecl, and build an application that uses it too. `test/` is a gdecl application of its own; `test/project/run_tests.gd` runs headless, first GDScript tests of Godot calling Lisp (classes in `test/lisp/classes.lisp`), then Lisp tests of Lisp calling Godot (`test/lisp/lisp-tests.lisp`, with `deftest` and `check`).
- The run fails if Godot reports leaked instances, resources in use or orphan StringNames at exit, so tests must free what they make (Lisp tests add their nodes to `*root*`), and if Godot reports an error no test expected, also at exit. A test that causes a Godot error on purpose prints `[test] expect error` just before it. The full log is `test/build/test.log`.
- `check` evaluates a call's arguments first, to show them on failure, so a literal string there is a runtime value, not an `sname`: wrap such a call in another (`(check (eq t (f "literal")))`).
- In GDScript, calling a method on a typed variable is a ptrcall (a failing method returns its type's default value, such as 0 for an int, not null; use `call` for a Variant call, which returns null), and lambdas capture locals by value.
- A test should fail without the change it tests: when fixing a bug, check that the new test fails on the old code.
- When refactoring a code generator (`define-engine-class`, `define-class`, …), compare the macroexpansions before and after, with `*gensym-counter*` reset before each, to show the generated code is unchanged. `make expansions-baseline` before and `make expansions-check` after do that for all engine methods and utility functions in `extension_api.json`, and for the invokers of bound methods of each type (`test/expansions.lisp`); extend it to cover other generators you change. It writes symbols with their home package, so changing what a package exports doesn't show as a change, but moving a symbol to another package does. A change to its output format needs a new baseline from the code before the change.

## Benchmarks

- `make bench` times calls between Lisp and Godot, and the same calls in GDScript (`test/lisp/benchmarks.lisp`, `test/project/run_benchmarks.gd`).
- Results vary by about 15% from run to run, and by 25% or more between sessions on the same machine, so a few runs of one build prove little. To see what a change costs, compare it with a build of `HEAD` in alternating runs: `git worktree add --detach <dir> HEAD` outside the repository, copy `extension_api.json` and `src/gdextension_interface.h` into it (git ignores them), run `make bench` in each tree in turn, four times or more, and remove the worktree afterwards.
- Typical times, in quiet runs on this machine: an engine method call from Lisp with only simple types 60–80 ns, allocating nothing (GDScript 17–30 ns); with a Vector2 argument 110–120 ns, a Vector2 result or an Object result 150–175 ns; a vararg one (`emit_signal`) 0.27–0.28 µs with its further arguments as a `&rest` list, 0.16 µs with `:extra-arguments` of simple types (GDScript 35 ns); a call into a Lisp method with ptrcall (like `_process`) 0.2 µs with a float argument, 0.15–0.16 µs into an empty one without (into a GDScript method 90 ns), with a Variant call 0.4–0.42 µs (0.32–0.34 µs without arguments, returning an int); a signal emitted to a Lisp handler 0.34–0.35 µs in all (with no handler 65 ns, with a GDScript handler 230 ns); a notification to a `notification` method 0.43–0.48 µs, and one that no class wants 31–33 ns, as for an engine class, since it doesn't enter Lisp; an empty `_process`, called through `NOTIFICATION_PROCESS`, 0.19–0.2 µs with `define-class` or a `godot-clos` direct function (0.32–0.35 µs before the callbacks took integers) and 0.44–0.45 µs through a generic function before (GDScript 91–95 ns, none 31–33 ns).
