# gdecl

Guidance for working on the gdecl framework: Godot 4 GDExtension programming in Common Lisp with ECL, without godot-cpp. User-facing documentation is in `README.md`; what each function does is in its docstring. This is its own repository (github.com/flambard/gdecl), used by applications as a git submodule, so keep it free of anything specific to an application.

## Goal and direction

GDExtension is a low-level C interface, not meant to be used directly by application developers. gdecl's goal is to raise the level of abstraction step by step until writing a Godot application in Lisp is at least as easy as with GDScript or C#, while staying efficient. Godot is mostly used for games, which are performance sensitive, so ease of use must not cost per-frame overhead.

Principles:

- **Build up gradually.** Each layer is built on the ones below it (see Layers), probably with one more layer on top of `gd-extension` later for the highest-level concepts (see The high-level layer below). Grow the framework from what the applications built on it need, and move code from an application into gdecl once the pattern is clear.
- **High level by default, drop down where it matters.** Applications should be able to program at a very high level, and drop down to lower-level concepts exactly where a task is performance sensitive, without giving up the high level elsewhere: one method of a high-level class, or one hot loop, can use a lower layer. So the layers must work together: high-level objects can be passed to everything below (as `godot-object`s are through `object-pointer`), a high-level class can have methods bound the low-level way, and the lower layers stay usable and documented. Speed is opt-in step by step: type declarations, non-allocating operations, dispatch resolved once.
- **Performance first: shift work from run time to compile time.** gdecl is for games, so every design is judged by what it costs per frame. Do at compile time (macros, code generated from `extension_api.json`) what can be done then, and at initialization or registration what has to wait for Godot (method binds, StringNames, constructors, cached once); keep only what must happen per call at run time. Prefer `ptrcall` to Variant calls, avoid allocating in calls that happen every frame (`_process`, `_physics_process`), and prefer deterministic, explicit resource handling (such as the autorelease pool, decided per method when the code is generated) to run-time machinery such as GC finalizers.
- **Improve gdecl as you go.** When an application needs something gdecl lacks, or something in it could be better, improve gdecl rather than working around it in the application. Keep such changes general.
- **Measure.** Before choosing a convenient but slower design for something called often, check what it costs.

Where to look for inspiration:

- **GDScript**: the API application developers know: `extends`, `@export`, `signal`, virtual methods such as `_ready` that you just define, `$Node` paths, `@onready`.
- **Godot C# (`GodotSharp`)**: the closest model, a garbage-collected binding. Engine classes are generated from `extension_api.json` with method binds cached in static fields, builtin types such as `Vector2` are implemented in C#, user classes use attributes and a source generator writes the registration code, and `RefCounted` lifetimes are tied to the managed object.

### The high-level layer: CLOS, a specialized DSL, or both (open)

The ambition is to program Godot at a high level in Lisp: Godot's object-oriented concepts (classes and inheritance, virtual methods, properties, signals) expressed naturally, at least as easy as GDScript and C#, and fast enough for games.

CLOS is the leading candidate, but not yet a decision. Godot's model is class-based like GDScript's and C#'s, and CLOS adds what they lack: generic functions with method combination (e.g. `:before` methods on `_ready`), the MOP for registering classes behind the scenes, and redefining classes in a running game (`update-instance-for-redefined-class`), which is probably Lisp's strongest selling point here. Something like:

```lisp
(define-godot-class player (sprite-2d)
  ((speed :initform 400.0 :type float :export t))
  (:signals (hit)))

(defmethod process ((self player) delta) ...)
```

The risk is per-frame cost. ECL's dynamic machinery is expensive per call (measured: a call to a function in another file about 50 ns, `handler-bind` about 250 ns), and generic function dispatch and `slot-value` are likely similar. So it may fit better to have a more specialized DSL, macros that compile Godot-specific definitions into tight code (as `define-class` and the invokers of `ptrcall-invoker-form` already do), or a hybrid: CLOS for defining and redefining, with dispatch resolved once (an effective method found per class and virtual, e.g. in `get_virtual_call_data`, not per call) and specialized code generated for the per-frame paths. `define-class` is already a small DSL, with a syntax meant to be able to expand into whichever fits, without changing applications much.

Whichever it is, dropping down must work from inside it (see the principles): a high-level class whose hot methods are written closer to the metal. Decide by measuring and prototyping, as for the FFI work: measure CLOS in ECL (a generic function call, `slot-value` against an accessor, `make-instance`, calling a precomputed effective method), and write a real class, such as the first game's Player, both ways, comparing ease of use and `make bench` numbers. Other open questions: a macro over `defclass` or a metaclass; generated classes for engine classes, and only for those used; mapping each Godot object to one Lisp wrapper (instance bindings), with RefCounted lifetimes tied to the wrapper (finalizers).

## Layers

From the bottom up; dependencies only go downwards. Packages are in `lisp/packages.lisp`, files in `gdecl.asd`.

- `gd-extension-ffi`: the GDExtension C interface, one-to-one, without Lisp conveniences. Each interface function is a variable named after the C function (`*string-name-destructor*`), set in `load-interface`, and a wrapper function of the same name without earmuffs. Also ECL foreign-memory helpers.
- `gd-extension-builtins` (`builtin-types.lisp`): Godot's builtin types (`vector2`, `basis`, …) in plain Lisp. Everything it exports is for applications: `gd-extension` and `godot` re-export all of it through an export list computed when `packages.lisp` is read, so a new symbol is exported in one place only.
- `gd-extension-types`: converting between raw values, Lisp values and Variants. `*value-types*` (by variant type) is the one table of how each type converts; add new types there, with `add-value-type`. A value type's `lisp-type` is how `write-variant` finds the variant type of a struct such as `vector2` or `callable`.
- **Adding a builtin type** (Color, Transform2D, …) takes three things: the struct, with a constructor that converts its components (Godot's `real_t` is single-float, but Lisp code computes with doubles), and its functions in `builtin-types.lisp`; their exports in `packages.lisp`; and a `define-builtin-type` form in `gd-extension-types.lisp`, which generates the FFI mirror of Godot's layout, `read-`/`write-` and the value type. Defaults such as `Vector2(0, 0)` in `extension_api.json` then work too, for types whose components are all floats.
- `gd-extension-callback`: everything Godot calls into, and the tables behind the callbacks, in six files loaded in this order: `gd-extension-callback.lisp` (`define-callback`, threads, `with-callback-protection`), `initialize.lisp` (`initialize` and `deinitialize`, called from `src/gdecl.c`, their hooks, and initialize cells), `instance-bindings.lisp` (`lisp-object`, the Object value type), `extension-classes.lisp` (classes, instances, which virtuals a class implements), `bound-methods.lisp` (methods and virtual methods, invokers, `call-virtual-with-data`) and `callables.lisp`. A function called on a per-call path from another of these files is declared `inline` (`instance-object`, `set-call-error`).
- `gd-extension`: the public, Lisp-style layer, in several files whose load order in `gdecl.asd` matters (see Startup and shutdown). `extension-api.lisp` reads `extension_api.json` at compile time with gdecl's own small JSON reader (`gdecl-json`).
- `godot` and `godot-utility`: Godot's API generated from `extension_api.json` (`define-engine-class`, `define-global-enums`, `define-utility-functions`). Applications add the engine classes they use to `godot`.

Consequences of the layering that aren't obvious:

- The types layer can't refer to the callback layer, so `gd-extension-callback` installs the Object reader (which maps instances to their Lisp objects) and the Callable writer with `add-value-type`.
- Releasing a reference needs an engine method, so `gd-extension` sets `*release-reference-function*` for the autorelease pool in the types layer.
- `gd-extension` can't depend on `godot`, so it defines the few engine methods it needs itself, and keeps its own `+connect-one-shot+`.

## Startup and shutdown

- `src/gdecl.c` boots ECL at `GDEXTENSION_INITIALIZATION_SCENE`, with ECL's signal trapping (SIGSEGV etc.) disabled so it doesn't fight Godot's handlers. Loading the Lisp code runs the application's top-level forms, which register its entry point with `add-initialize-hook`. The C side then calls `gd-extension-callback:initialize`, the only Lisp function it knows, which loads the interface, fills in the initialize cells, and runs the initialize hooks. gdecl's own hook, which registers the classes from `define-class`, is added first, so the classes are registered before the application's hooks run.
- At deinit, `deinitialize` runs the deinitialize hooks in reverse order while Godot can still be called, then ECL is shut down. gdecl's own hooks are added before the application's, so they run last: `unregister-singletons` (`registration.lisp`, which frees the singletons' instances while their classes are still there), `unregister-classes` (`registration.lisp`, subclasses first), then `destroy-permanent-values` (`gd-extension.lisp`, the StringNames and NodePaths from `sname`, `npath` and class names). That order depends on the load order in `gdecl.asd`. With both, Godot reports no leaks at exit; the one orphan `Node` the editor reports is Godot's own.

## Rules and pitfalls

- **Nothing is looked up in Godot at load time.** ASDF loads gdecl into the build image to compile what depends on it, and there's no Godot there. Lookups go into initialize cells (`initialize-cell-value`), filled in by `initialize`, or right away at a REPL. The cells are filled in before the initialize hooks run, so before the classes are registered: a lookup of something the extension registers itself must wait until it's used, as `singleton` does (singletons from `register-singleton`).
- **A Lisp error must never unwind through Godot's C frames.** Wrap every callback body in `with-callback-protection`, which catches errors, reports them with `report-error` (Godot's `print_error`, so it shows in the editor). A bound method that fails returns null with `CALL_OK`, like a failing GDScript method; `CALL_ERROR_INVALID_METHOD` would make Godot say the method doesn't exist.
- **ECL FFI:** a `:pointer-void` returned by a foreign function has no size, so cast it before accessing slots (`cast-pointer`, `foreign-ref`). `defcallback` rejects `:uint8-t`, so declare `GDExtensionBool` as `:unsigned-byte`. Check new struct mirrors against C with `sizeof`/`offsetof`. `doc/package-ffi-symbols.txt` and `doc/package-si-symbols.txt` list what ECL's `FFI` and `SI` export.
- **ECL's FFI does at runtime what can be done at compile time, and it's slow** (measured: `get-slot-value` about 5 µs, the size of a struct type about 4 µs, `si:call-cfun` 0.6 µs, `with-foreign-object` 0.6 µs plus the size). On paths that run per call, use gdecl's replacements, which generate C code with `ffi:c-inline`: `call-foreign-pointer` (and `define-interface-function`) instead of `si:call-cfun`, `with-foreign-memory` instead of `ffi:with-foreign-object(s)`, `set-foreign-slots` instead of `(setf (ffi:get-slot-value …))` (it also works on pointers without a size), and `foreign-ref`, `clear-foreign-object` and `array-element` with a constant type, which compiler macros turn into C (compiler macros only apply in files other than the one defining the function, so not inside `gd-extension-ffi.lisp`). Avoid `get-slot-value`, `element-pointer`, `cast-pointer` and `size-of-foreign-type` there; registration code can use them. Pointers from `with-foreign-memory` and `c-inline` have no size, so `cast-pointer` them before `get-slot-value`. C code in `c-inline` can't rely on headers, so use `__builtin_memset` and the like. C code in `ffi:clines` belongs to its file: ASDF compiles each file into a library of its own to load into the build image, so another file can't call a C function or use a variable defined there, not even a non-static one. Pass an address through Lisp instead, as `define-callback` does with `enter-lisp-address`. An `inline` function with `&key` arguments is slower than not inlining it, as ECL's inlined code parses the keywords at run time (measured: 50 ns on a Lisp signal handler); use `&optional` arguments for inline functions.
- **Sizes and layouts** come from the `float_64` build configuration in `extension_api.json`: `real_t` is `float`. The FFI mirrors, generated by `define-builtin-type`, are named `godot-vector2` etc., so the plain names are free for the Lisp types.
- **Basis:** Godot stores the rows, but the Lisp `basis` has the columns, as `basis.x` and `Basis(x, y, z)` in GDScript; `read-basis` and `write-basis` transpose.
- **ptrcall:** every argument must be given, defaults too. An Object argument is a pointer to the object pointer. A float is always a double and an int an `int64_t`, whatever the `meta` in `extension_api.json`. Zero the return slot first: Godot assigns into it (`Ref<T>`, `PackedStringArray`), releasing the old value. Vararg methods can't be ptrcalled.
- **One Lisp object per Godot object.** Every Object that Godot gives Lisp is mapped to its Lisp object through Godot's instance bindings (`lisp-object`, `instance-bindings.lisp`): an instance of an extension class to the struct its constructor made (the binding is set in `create-class-instance`), any other object to a Lisp object made on first sight (`create-binding`, which calls `*wrapper-function*`): a struct of the type of its class (`engine-objects.lisp`). `define-engine-class` defines a struct per class, which includes that of the nearest class it inherits from that's defined, so they mirror Godot's inheritance and `typep`, `typecase` and `defmethod` work; `define-class` includes the struct of its engine parent class. A new object's type is found by walking Godot's class parents (a table from `extension_api.json`, made when gdecl is compiled) to the nearest class with a struct, cached by the address of the class name's StringName data, which is the same for the same name while the class is registered. Godot calls `free-binding` when it frees the object, which clears the Lisp object's pointer, so `object-pointer` signals an error for it. `free-bindings`, a deinitialize hook that runs last, frees the remaining bindings before ECL shuts down; otherwise Godot would call `free-binding` after it, e.g. for engine singletons. Code that passes an object to Godot must go through `object-pointer` (`singleton` returns a Lisp object too). Raw pointers are still accepted wherever an Object is passed to Godot, for dropping down, but not where a Variant is made from a Lisp value (`lisp-variant-type`): a raw pointer might point to something else, such as a StringName.
- **Godot calls into Lisp from any thread.** Define callbacks with `define-callback`, not `ffi:defcallback`, and give Godot `callback-pointer`: it puts a C function in front that imports the thread into ECL the first time (otherwise ECL aborts the process), and releases it when the thread exits (otherwise the next GC aborts). Only the callbacks are thread-safe so far, not the tables behind them (TODO R).
- **Callbacks are on the per-frame path.** `with-callback-protection` replaces `handler-case` and `with-autorelease-pool` there: ECL's `handler-bind` conses a handler cluster at every entry (about 250 ns), so it binds ECL's internal `si:*handler-clusters*` to a cluster made once, and exits with `catch`. It needs no `unwind-protect`, since nothing but an error can leave a callback. Bound and virtual methods whose types are known when the code is compiled (`bind-virtual`, and `define-class` with constant types) get an invoker generated for their signature (`ptrcall-invoker-form`), so `ptrcall-bound-method` doesn't build an argument list, `apply`, or call converters by name; `bind-method` called with types at runtime uses the generic path. The user's function is still called by name, so redefining it takes effect.
- **Arrays and dictionaries are copies** (`containers.lisp`): packed arrays of numbers are specialized Lisp vectors, copied with `memcpy` and no conversion per element; other packed arrays and Arrays are simple vectors, converted element by element; Dictionaries are `equal` hash tables. Their conversions need Godot's builtin methods (`size`, `resize`, `keys`, looked up with `builtin-method`, hashes from `extension_api.json`), so they're added to `*value-types*` from `gd-extension`. Writers take any sequence, so `#()` is the default value of an empty array argument.
- **Unsupported types:** when the code generator meets a type it can't convert yet, it signals `unsupported-api-type`. `define-engine-class`, `define-utility-functions` and `bind-virtual` skip only that condition, so any other error, such as a bug in the generator, stops the build instead of making methods silently disappear.
- **Method hashes** come from `extension_api.json`; `classdb_get_method_bind` returns NULL on a mismatch, which usually means the JSON was dumped from another Godot version.
- **Virtual methods** use `get_virtual_call_data_func`, which returns NULL for those the class doesn't implement, so Godot never calls into Lisp for nothing. Several engine classes have virtuals with the same name but different signatures (`_process`), and the parent class isn't known when `bind-virtual` expands, so the expansion carries all of them and the right one is picked at registration.
- **Godot can't register a class twice**, so redefining a class at a REPL doesn't work yet. Functions given to `define-class` as symbols are called by name, so redefining those does.
- **Literal names:** a compiler macro wraps literal strings given for StringName and NodePath arguments in `sname`/`npath`. That doesn't apply through `funcall`/`apply`, or to calls compiled before the definition; then each call makes a temporary one.
- **Callables:** `object_id` must be set, since Godot skips connections without an object. Godot doesn't initialize `r_error` for custom Callables, so it's always set. A result that can't be a Variant becomes null, not an error, since Godot ignores signal handlers' results.
- **Variant calls into bound methods** accept null for an Object, and a float for an int (truncated) or an int for a float, as Godot does for its own methods.

## References (RefCounted ownership)

- An engine method's RefCounted result comes with a reference (a `Ref<T>`). During a call from Godot (every callback and every initialize/deinitialize hook) it goes into the autorelease pool and is given back when the call returns. Outside a call, e.g. at a REPL, there's no pool and the caller owns it.
- An Object Variant result: the Variant is copied and the copy is kept until the pool goes, which keeps the reference without having to ask Godot whether the object is RefCounted.
- An Object a bound or virtual method returns with ptrcall needs a reference for Godot (`reference-for-caller`): Godot puts the pointer into a Variant or `Ref<T>` without taking one, and gives one back later. Without it, a typed GDScript call of a RefCounted getter released a reference it never got.
- Arguments never take a reference: the caller owns those Variants.
- `setf-reference` takes the new reference before giving back the old one, in case they're the same object.

## Build

- `gdecl.mk` builds the application's ASDF system monolithically into `$(BUILD_DIR)/application.a`, always with the init function `init_lib_APPLICATION`, which `src/gdecl.c` calls by name; keep the two in sync. `application.a` must come before ECL's flags (`-lecl`) when linking.
- Changing `SYSTEM` doesn't make `application.a` out of date; use `make -B`.
- `src/gdextension_interface.h` and `extension_api.json` are generated by Godot (`make godot-api`) and ignored by git; don't edit them. The `EditorSettings not instantiated yet` error while dumping is harmless.

## Tests

- Run `make test` after changing gdecl. `test/` is a gdecl application of its own; `test/project/run_tests.gd` runs headless, first GDScript tests of Godot calling Lisp (classes in `test/lisp/classes.lisp`), then Lisp tests of Lisp calling Godot (`test/lisp/lisp-tests.lisp`, with `deftest` and `check`).
- The run fails if Godot reports leaked instances, resources in use or orphan StringNames at exit, so tests must free what they make (Lisp tests add their nodes to `*root*`). A test that causes a Godot error on purpose prints `[test] expect error` just before it. The full log is `test/build/test.log`.
- `check` evaluates a call's arguments first, to show them on failure, so a literal string there is a runtime value, not an `sname`: wrap such a call in another (`(check (eq t (f "literal")))`).
- In GDScript, calling a method on a typed variable is a ptrcall (a failing method returns 0 for an int, not null; use `call` for a Variant call), and lambdas capture locals by value.
- When refactoring a code generator (`define-engine-class`, `define-class`, …), compare the macroexpansions before and after, with `*gensym-counter*` reset before each, to show the generated code is unchanged.

## Measured costs

- Each engine method is a compiled function with its own conversion code: about 55 ms of build time and 10 KB of object code per method (measured with Control's ~130 methods, after the inline calls); the game's library is 6.3 MB. Shared callers per signature with small per-method wrappers would be smaller, but would add a call between files (about 50 ns) to every engine call, a third of a simple one, so per-method code stays; if size becomes a problem, predefine fewer classes.
- Reading `extension_api.json` takes about half a second per build.
- `make bench` times calls between Lisp and Godot, and the same calls in GDScript (`test/lisp/benchmarks.lisp`, `test/project/run_benchmarks.gd`). On this machine: an engine method call from Lisp with only simple types about 140–160 ns and no allocation (GDScript 50–100 ns), with a Vector2 argument 240 ns, a Vector2 result 360–400 ns, an Object result 340 ns, other types (String, Variant, …) 0.5–0.8 µs, a vararg one (`emit_signal`) 1.7 µs (GDScript 150 ns), a call into a Lisp method with ptrcall (like `_process`) 0.7–0.9 µs (into a GDScript method 0.3 µs; an empty callback alone costs 0.3 µs), and a Lisp signal handler 1.3–1.7 µs on top of the emit (a GDScript handler 0.45 µs; Godot's dispatch to an empty custom Callable 0.4 µs). Run to run, results vary by about 15%, so compare several runs. In ECL, a call of a function defined in another file costs about 50 ns (it goes through the symbol), so on hot paths a few small cross-file calls add up: declare small helpers `inline` (as `find-value-type`), and convert primitive types' Variants in one piece of C (`variant-reader`/`variant-writer` of value types). Engine methods whose types are all simple (bool, int, float, Object, StringName and NodePath arguments, and builtin types made of floats, about 80% of them) are called in one `c-inline` with C variables for the raw values and the argument array (`inline-ptrcall-form`), so they allocate nothing but the result's Lisp value; the others go through foreign memory (`general-ptrcall-method-form`), a `malloc` and a Lisp pointer object for each raw value. Measure with `make bench` before and after optimizing.
