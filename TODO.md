## Performance (measure with `make bench` before and after)

Where things stand: an engine call from Lisp with only simple types costs 140–160 ns and allocates nothing (GDScript: 50–100 ns), with a Vector2 result 360–400 ns, with other types (String, Variant, …) 0.5–0.8 µs, a vararg one (`emit_signal`) 1.7 µs (130 ns), a call into a Lisp method with ptrcall, like `_process`, 0.7–0.9 µs (into a GDScript method: 0.25 µs; an empty callback alone: 0.3 µs), and a Lisp signal handler 1.3–1.7 µs on top of the emit (a GDScript handler: 0.45 µs). Results vary by about 15% from run to run.

- [ ] **N. The rest of a call into Lisp.** Of the 0.7–0.9 µs of a ptrcall, about 0.3 µs is the method and instance lookups (`userdata-method`, `instance-object`), boxing a float argument as a Lisp double, and calling the user's function by name, which is what makes redefinition work. A Lisp signal handler (`callable-call`) costs 1.3–1.7 µs on top of the emit, of which Godot's dispatch to a custom Callable is 0.4 µs; the rest is spread over small steps (the protection, `set-call-error`, `read-variant` for each argument, `apply`, writing the result as a Variant), each tens of nanoseconds, mostly calls between files (about 50 ns each in ECL). Measure each before changing anything.
- [ ] **O. Variant calls into Lisp have no invokers.** `call-bound-method` (a call through `call()` or an untyped GDScript variable, about 1.5 µs) still builds an argument list and converts each argument through the value-type table. Invokers like `ptrcall-invoker-form`'s would help, but Variant calls are rarely per frame.

## The high-level layer (see "The high-level layer" in `CLAUDE.md`)

- [ ] **P. CLOS or a specialized DSL: measure and prototype.** Before building more on `define-class`, measure CLOS in ECL with micro-benchmarks like those for the FFI work: a generic function call with one and two specialized arguments, `slot-value` against an accessor, `make-instance`, and calling an effective method computed once. Then write one real class, such as the game's Player, both with CLOS and with `define-class`, and compare ease of use and `make bench` numbers. Include dropping down: one hot method of the class written at a lower level (no generic dispatch, typed, non-allocating), to see that it can be done cleanly inside a high-level class. That decides between CLOS, a specialized DSL or a hybrid, and whether the structs of engine objects (`engine-objects.lisp`, which `defmethod` can already dispatch on) should become CLOS classes. It shapes J too.
- [ ] **J. Tables keyed by name, updated in place (with the REPL work).** `*bound-methods*`, `*extension-classes*`, `*instances*`, `*callables*` and `*bindings*` (`gd-extension-callback.lisp`) are hand-written, append-only and keyed by `(1+ index)` pointers. Redefining a class at a REPL adds a duplicate entry, `add-virtual` finds the stale first one, and re-registered methods are never replaced. Use one table abstraction, key classes and methods by name, and update entries in place. Godot caches `get_virtual_call_data`, so a virtual added later isn't picked up. Redefining a struct with changed slots is undefined: an argument for `defclass` in the high-level layer.

## Gaps

- [ ] **R. Calls from other threads.** Godot calls into Lisp from threads other than the main one: Callables on `Thread` and `WorkerThreadPool`, `_process` of nodes in a thread group, instances made by threaded resource loading, objects freed on another thread. Done: `define-callback` imports a thread into ECL the first time it calls in, and releases it when it exits (`make test` runs Callables on both). Left:
  - The tables behind the callbacks (`*instances*`, `*bindings*`, `*callables*` and their free lists, `*bound-methods*`, `*extension-classes*`) aren't thread-safe: `vector-push-extend`, `push` and `pop` race, e.g. `callable-free` on a worker thread while the main thread makes a Callable can give two Callables the same index. A lock on every read would cost about 85 ns (an `aref` is 6 ns), too much for the per-frame path. Instead, since ECL's GC doesn't move objects, the handles given to Godot could be the Lisp objects' addresses (1.7 ns to turn back into the object), kept reachable in a table locked only when adding and removing. Do it with J.
  - `*class-name-constructors*` (`engine-objects.lisp`) is filled in by `create-binding`, on any thread: `:synchronized t` (38 ns against 11 ns for `gethash`) or a lock only when filling it in. Never call Godot while holding a Lisp lock: Godot holds its own around `create-binding`.
  - Getting back to the main thread, where most of Godot's scene API must be called: `call-deferred` with a Lisp function, `call-deferred-thread-group`, and wrappers for `WorkerThreadPool`. A REPL (Swank) runs in a thread of its own, so it needs this too.
  - A thread still in Lisp when ECL shuts down isn't waited for.
- [ ] **S. Shipping a game.** An exported game can't load the extension. The `.gdextension` files (the application's and `test/project/`'s) list only `linux.debug`, so a release export has no library; `gdecl.mk` should build one and the README should show the `linux.release` entry. `libgdecl.so` links `libecl.so` and `libgc.so` dynamically, so players would need ECL installed: bundle them next to the library (with an `$ORIGIN` rpath, and the `[dependencies]` section of the `.gdextension` so Godot exports them), or link ECL statically. Only Linux is built; Windows and macOS need ECL built for them (cross-compiling or CI), and the web would need ECL for Emscripten.
- [ ] **T. Callable and Signal values into Lisp.** Callable only converts from Lisp to Godot (`write-callable`), and Signal not at all, so `read-variant` signals "Unsupported type for a Variant" when one reaches Lisp: a signal handler's argument, a Variant result, an element of an Array or Dictionary. This is also why 9 methods with Callable results are skipped. Read a Callable as a Lisp object that can be called (`callable_call` through the Variant), compared and passed back; a Lisp custom Callable could be read back as its `callable` struct, by `callable_custom_get_userdata` with gdecl's token. Signal: an object and a signal name, with functions to connect and emit.
- [ ] **U. A Lisp class extending a Lisp class.** Untested, and probably broken. `define-class` gets the struct to include from `engine-object-type`, which looks the parent up only in `extension_api.json`, so with a parent like `"Player"` the struct includes only `godot-object`: not the parent's slots, and `typep` against the parent's struct fails. Virtuals aren't inherited either: `virtual-call-data` looks only at the class's own (`add-virtual`), so a subclass that doesn't define `_process` loses its parent's. Whether Godot calls the parent extension class's `create_instance` also needs checking. Ties in with P: with CLOS, inheritance would come from `defclass`.
- [ ] **V. More of GDScript in `define-class`.**
  - `_notification`, `_get`, `_set`, `_get_property_list`, `_property_can_revert`, `_validate_property` and `_to_string` aren't virtual methods in GDExtension but slots of `class-creation-info4` (`notification-func` etc.), which `register-class` leaves NULL. So a class can't react to notifications (e.g. `NOTIFICATION_PREDELETE`, `NOTIFICATION_PARENTED`) or have dynamic properties. Add them as `define-class` options with callbacks like `call-virtual-with-data`'s.
  - `:export` has no hints: `@export_range`, `@export_enum`, `@export_file`, `@export_multiline`, `@export_flags`, and no `@export_group` or `@export_category` (properties with `PROPERTY_USAGE_GROUP`). `bind-property` already takes a hint and hint string, so `define-class` only needs to pass them on.
  - Bound methods have no default arguments (`default-argument-count` is 0), and can't be static (`+method-flag-static+`) or vararg.
  - Classes can't be abstract or virtual (`is-abstract`, `is-virtual`), or have an editor icon (`icon-path`).
  - A Lisp class can't declare virtual methods of its own for GDScript subclasses to override (`classdb_register_extension_class_virtual_method`, and `GDVIRTUAL_CALL` on the Lisp side).
- [ ] **W. Methods of builtin types.** Vector2, Vector3 and Basis have a few functions in Lisp (`builtin-types.lisp`); Color, Transform2D, Transform3D, Quaternion, Rect2, AABB, Plane and the integer vectors have only constructors and accessors, so nothing like `Color.lerp`, `Transform2D.basis_xform` or `Rect2.has_point`. The hot ones belong in Lisp (no call into Godot), and the rest could be generated from `extension_api.json` like engine methods: a `define-builtin-method` on `call-ptr-builtin-method`, which `containers.lisp` already uses for a few.
- [ ] **X. Extension points beyond classes.** gdecl starts only at the scene level (`initialize_gdecl_module` in `src/gdecl.c` returns at the other levels), and its classes are game classes. Not possible yet:
  - Editor plugins: classes extending `EditorPlugin`, `EditorInspectorPlugin` or `EditorExportPlugin` must be registered at the editor level and added with `editor_add_plugin`. Needs initialize hooks per level, and ECL already booted then (it is, from the scene level).
  - Lisp as a script language, attached to nodes like GDScript: a `ScriptLanguageExtension` and a `ScriptExtension` (60 and 37 virtual methods) and script instances (`script_instance_create3`). A large piece of work; worth it only if attaching scripts to nodes in the editor matters more than `define-class`.
  - Singletons: `Engine.register_singleton` with an instance of a Lisp class, unregistered at deinit. Possible today with `(define-engine-class "Engine")` and an initialize hook; a `define-class` option would make it one line. (An autoload works now with a scene whose root is a Lisp class.)

## Suggested order

1. S before shipping anything: an exported game doesn't run without it.
2. P: the high-level layer is gdecl's ambition, so decide its direction before building more on `define-class`. Its measurements are cheap. It also decides U and much of V.
3. N: calls into Lisp (0.7–0.9 µs) are now the biggest cost per frame left.
4. T, U, V and W as applications need them; T's Callable results and V's `_notification` and export hints are the likeliest.
5. O, if measurements show it matters.
6. J with the REPL work, and R when an application uses threads.
7. X when there's a reason to extend the editor.
