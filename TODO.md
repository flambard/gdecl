# TODO

What's left to do in gdecl, from reviews and from comparing what gdecl does with what a game needs. Items keep their letters when others are done, so they can be referred to (e.g. "TODO R" in `CLAUDE.md`); finished items move to Done at the end. File references are to files in the layers' directories under `lisp/` (see Layers in `CLAUDE.md`) unless shown otherwise. gdecl's first principle applies to all of it: performance first, and shift work from run time to compile time (`CLAUDE.md`).

## Performance

Measure with `make bench` before and after, against a build of `HEAD` in alternating runs (see Benchmarks in `CLAUDE.md`). Where things stand, in quiet runs: an engine call from Lisp with only simple types costs 60–80 ns and allocates nothing (GDScript: 17–30 ns); with a Vector2 argument 110–120 ns; with a Vector2 or Object result 150–175 ns; a vararg one (`emit_signal`) 0.85–0.9 µs (GDScript: 35 ns); a call into a Lisp method with ptrcall, like `_process`, 0.3–0.35 µs (into a GDScript method: 90 ns), and with a Variant call 0.55–0.6 µs; a signal emitted to a Lisp handler 0.69–0.75 µs in all (with a GDScript handler: 230 ns, with none: 65 ns).

- [ ] **N. The rest of a call into Lisp.** A ptrcall into a Lisp method costs 0.3–0.35 µs, against 90 ns into a GDScript method. The lookups are inline now (`handle-tables.lisp`); what's left per call is the C function in front of the callback (`gdecl_enter_lisp`, through a pointer), `with-callback-protection` (a `catch`, and binding `si:*handler-clusters*` and the autorelease pool), boxing a float argument as a Lisp double, and calling the user's function by name, which is what makes redefinition work. A signal emitted to a Lisp handler costs 0.69–0.75 µs in all, against 230 ns with a GDScript handler: `callable-call` reads each argument with `read-variant`, `apply`s the function, and writes the result as a Variant; Godot's own dispatch to a custom Callable was about 0.4 µs when last measured, before the recent speed-ups. Measure each step (an empty callback first) before changing anything.
- [ ] **O. Variant calls into Lisp have no invokers.** `call-bound-method` (a call through `call()` or an untyped GDScript variable, 0.55–0.6 µs against 0.3–0.35 µs with ptrcall) still builds an argument list and converts each argument through the value-type table. Invokers like `ptrcall-invoker-form`'s would help, but Variant calls are rarely per frame.
- [ ] **AH. Vararg engine calls.** `emit_signal` from Lisp costs 0.85–0.9 µs and allocates 336 bytes, against 35 ns in GDScript, about 25 times as much, and signals are often emitted per frame. `variant-call-method-form` allocates its argument array, the Variants and the raw values in foreign memory (a `malloc` and a Lisp pointer object each), writes the arguments of type Variant, such as all of `emit_signal`'s further arguments, with `write-variant` (by their Lisp types, at run time), and destroys every Variant afterwards. Arguments declared with `:extra-arguments` have known types, so their Variants could be made in one piece of C on the C stack, as `inline-ptrcall-form` does for ptrcall, and the result read the same way. Measure where the time goes first.
- [ ] **AI. Results that allocate.** A Vector2 or Object result costs 150–175 ns against 60–80 ns for an int, mostly the Lisp value made for it (112 bytes for a Vector2), and an Object result also asks Godot for the instance binding. For hot loops, functions that store a builtin result into a struct the caller gives (`node-2d-get-position-into`?) would allocate nothing, in line with dropping down where it matters (with AM).

## The high-level layer (see "The high-level layer" in `CLAUDE.md`)

- [ ] **AM. Faster slot access in CLOS classes, when an application needs it.** A CLOS accessor is a generic function call, 80 ns for an `incf`, against 25 ns with a struct accessor. For now, hot code drops down by keeping its data in a struct the object holds in one slot (see the README, Classes as CLOS classes), and the game shows that the calls into Lisp, not slot access, cost the most per frame. If an application needs more: (2) a `with-fast-slots` macro that looks up each slot's location once (a `gethash` in the class's location table, about 20 ns) and then uses `standard-instance-access`, for loops; or (3) inlined accessors per class, which check the instance's class and layout and fall back to the generic accessor. Both have to bring an instance up to date first after its class was redefined at a REPL, which ECL does lazily, on the next slot access through the usual paths, and to allow for subclasses and mixins that put an inherited slot at another location; ECL inlines the accessors of sealed classes only at `(safety 0)`, and sealing rules out redefinition. Measure with `make bench` (`CLOS: (incf (clos-benchmarks-ticks self))`).
- [ ] **AN. Rounding out `godot-clos`.** Invokers for the generated property getters and setters, which use the generic path (`bind-method` with types at runtime); `make-instance` of a RefCounted class, which signals an error now; and V in CLOS style.
- [ ] **J. Tables keyed by name, updated in place (with the REPL work).** The handle tables (`handle-tables.lisp`) are keyed by `(1+ index)` pointers, and those of classes and methods (`*extension-classes*`, `*bound-methods*`) are append-only. `godot-clos` works around that: it records what it has registered for each class and registers only what's new when a class is redefined at a REPL or a method added (`godot-registration.lisp`). `define-class` can't be evaluated again, which Godot refuses, and gets no REPL redefinition (P). Left: key classes and methods by name, and update entries in place, in `handle-tables.lisp` (with R); and Godot caches `get_virtual_call_data`, so a virtual method a class implements only after Godot first asked isn't called.

## Gaps

- [ ] **R. Calls from other threads.** Godot calls into Lisp from threads other than the main one: Callables on `Thread` and `WorkerThreadPool`, `_process` of nodes in a thread group, instances made by threaded resource loading, objects freed on another thread. Done: `define-callback` imports a thread into ECL the first time it calls in, and releases it when it exits (`make test` runs Callables on both). Left:
  - The handle tables behind the callbacks (`handle-tables.lisp`) aren't thread-safe: `vector-push-extend`, `push` and `pop` race, e.g. `callable-free` on a worker thread while the main thread makes a Callable can give two Callables the same index. A lock on every read would cost about 85 ns (an `aref` is 6 ns), too much for the per-frame path. Instead, since ECL's GC doesn't move objects, the handles given to Godot could be the Lisp objects' addresses (1.7 ns to turn back into the object), kept reachable in a table locked only when adding and removing. Do it with J; both change only `handle-tables.lisp`.
  - `*class-name-constructors*` (`engine-objects.lisp`) is filled in by `create-binding`, on any thread: `:synchronized t` (38 ns against 11 ns for `gethash`) or a lock only when filling it in. Never call Godot while holding a Lisp lock: Godot holds its own around `create-binding`.
  - Getting back to the main thread, where most of Godot's scene API must be called: `call-deferred` with a Lisp function, `call-deferred-thread-group`, and wrappers for `WorkerThreadPool`. A REPL (Swank) runs in a thread of its own, so it needs this too.
  - A thread still in Lisp when ECL shuts down isn't waited for.
- [ ] **S. Shipping a game** (low priority for now; see Suggested order). An exported game can't load the extension.
  - The `.gdextension` files (the application's and `test/project/`'s) list only `linux.debug`, so a release export has no library; `gdecl.mk` should build one and the README should show the `linux.release` entry.
  - `libgdecl.so` links `libecl.so` and `libgc.so` dynamically, so players would need ECL installed: bundle them next to the library (with an `$ORIGIN` rpath, and the `[dependencies]` section of the `.gdextension` so Godot exports them), or link ECL statically.
  - Only Linux is built; Windows and macOS need ECL built for them (cross-compiling or CI), and the web would need ECL for Emscripten.
- [ ] **V. More of GDScript in `godot-clos`.** Most of this needs support in `gd-extension`'s registration (`registration.lisp`), and then a slot or class option in `godot-clos`. `define-class` gets an option only where that's cheap, as it gets no new high-level features (P).
  - `_get`, `_set`, `_get_property_list`, `_property_can_revert`, `_validate_property` and `_to_string` aren't virtual methods in GDExtension but slots of `class-creation-info4` (`get-func` etc.), which `register-class` leaves NULL. So a class can't have dynamic properties. Add callbacks for them like `call-virtual-with-data`'s, and options in both class layers. `_notification` is done (`register-class`'s `:notification`, and `notification` in `godot-clos`), but `define-class` has no option for it yet. Its `:destructor` runs in `free_instance`, from Godot's `Object` destructor, so it can't call Godot; `NOTIFICATION_PREDELETE` is the place for that.
  - `:export` has no hints in either class layer: `@export_range`, `@export_enum`, `@export_file`, `@export_multiline`, `@export_flags`, and no `@export_group` or `@export_category` (properties with `PROPERTY_USAGE_GROUP`). `bind-property` already takes a hint and hint string, so the class layers only need to pass them on.
  - Bound methods have no default arguments (`default-argument-count` is 0), and can't be static (`+method-flag-static+`) or vararg.
  - Classes can't be abstract or virtual (`is-abstract`, `is-virtual`), or have an editor icon (`icon-path`).
  - A Lisp class can't declare virtual methods of its own for GDScript subclasses to override (`classdb_register_extension_class_virtual_method`, and `GDVIRTUAL_CALL` on the Lisp side).
- [ ] **W. Methods of builtin types.** Vector2, Vector3 and Basis have a few functions in Lisp (`builtin-types.lisp` in `types/`); Color, Transform2D, Transform3D, Quaternion, Rect2, AABB, Plane and the integer vectors have only constructors and accessors, so nothing like `Color.lerp`, `Transform2D.basis_xform` or `Rect2.has_point`. The hot ones belong in Lisp, in `gd-extension-builtins` (no call into Godot). The rest could be generated from `extension_api.json` like engine methods: a `define-builtin-method` in `gd-extension`, on `call-ptr-builtin-method`, which `containers.lisp` already uses for a few, generating into `godot` like `define-engine-class`. `extension-api-json` already reads the builtin types' methods into `api-method`s; it only looks up their hashes (`api-builtin-method-hash`) so far.
- [ ] **X. Extension points beyond classes.** gdecl starts only at the scene level (`initialize_gdecl_module` in `src/gdecl.c` returns at the other levels), and its classes are game classes. Not possible yet:
  - Editor plugins: classes extending `EditorPlugin`, `EditorInspectorPlugin` or `EditorExportPlugin` must be registered at the editor level and added with `editor_add_plugin`. Needs startup steps per level (`lifecycle.lisp`), with ECL already booted then (it is, from the scene level).
  - Lisp as a script language, attached to nodes like GDScript: a `ScriptLanguageExtension` and a `ScriptExtension` (60 and 37 virtual methods) and script instances (`script_instance_create3`). A large piece of work; worth it only if attaching scripts to nodes in the editor matters more than `define-class`.

## Suggested order

1. AH and N: a vararg call from Lisp (0.85–0.9 µs, `emit_signal`) and calls into Lisp (0.3–0.75 µs) are now the biggest costs per frame left.
2. AN, V and W as applications need them; V's export hints are the likeliest.
3. O, if measurements show it matters.
4. J with the REPL work, and R when an application uses threads.
5. AM when an application's hot code needs faster slot access than a struct gives.
6. X when there's a reason to extend the editor.
7. S, low priority for now: shipping a game isn't a concern yet. Do it before the first exported game, which doesn't run without it.

- From the restructuring of 2026-10-17: the layers as directories of `lisp/`, each a module of `gdecl.asd` that lists the layers it uses, with its packages in its own `package.lisp`; `define-class` in a layer of its own, `godot-dsl`, beside `godot-clos`, which gives the high-level layer packages of its own (from P); `extension_api.json` read into Lisp structs in one layer, `extension-api`, which `ffi` no longer depends on (the sizes of Godot's opaque values moved to `types`); the class layers built on `gd-extension` and `godot` only (`invoker-form`, `report-error`, and where a `godot-object` keeps its pointer); unused exports and imports removed; the game ported to `godot-clos`.
- AJ: `define-builtin-type` checks, when the code is compiled, that a builtin type's components add up to its size in `extension_api.json`.
- AK: `make expansions-check` writes symbols with their home package, so changing what a package exports doesn't show as a change.
- T: Callables and Signals into Lisp: a Callable read from Godot is the Lisp `callable` it was made from, or an `engine-callable` with a copy, valid until the call returns unless kept (`keep-callable`, `free-callable`), called with `call-callable` and compared with `callable=`; a Signal is an `engine-signal` (object and name), emitted and connected with `emit-engine-signal` and `connect-engine-signal`. With them, the 9 engine methods with Callable results and `Tween.tween_await` are no longer skipped; only the 3 with raw pointers are.
- AL: a bound or virtual method that fails when called with ptrcall returns its type's default value (`write-failed-result`), not what was left where the caller keeps the result.
- P, decided on 2026-10-17: CLOS, `godot-clos`, is the high-level layer, with a fast path for dropping down (AM); `define-class` (`godot-dsl`) stays as a faster, lower layer, without new high-level features. A call from Godot into a generic function costs 0.53–0.54 µs against 0.35–0.39 µs into a `define-class` function: 0.2 ms a frame for 1,000 objects with `_process`, about 1%, small next to what entering Lisp costs at all (N), while CLOS gives inheritance, mixins, method combination and redefinition at a REPL. The game is written with it.
- U: a Lisp class extending a Lisp class works with `godot-clos`, which binds the inherited virtual methods itself, and is tested; `define-class` doesn't get it (P).
- AM's first part: a `godot-class` can bind a virtual method to a plain function, `(:direct-functions (physics-process function))`, inherited by subclasses; measured with `make bench`, an empty `_process` costs 0.33–0.35 µs that way, as with `define-class` (0.32–0.35 µs), against 0.44–0.45 µs through the generic function.
