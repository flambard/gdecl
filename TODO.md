What's left to do in gdecl, from reviews and from comparing what gdecl does with what a game needs. Items keep their letters when others are done, so they can be referred to (e.g. "TODO R" in `CLAUDE.md`); finished items move to Done at the end, until what was learned from them is written into `CLAUDE.md` and Done is emptied. ## The high-level layer (see "The high-level layer" in `CLAUDE.md`)

- [ ] **AM. Faster slot access in CLOS classes, when an application needs it.** A CLOS accessor is a generic function call, 80 ns for an `incf` against 25 ns with a struct accessor. For now hot code keeps its data in a struct held in one slot, and a hot virtual method is bound to a plain function (`:direct-functions`); the game shows that calls into Lisp, not slot access, cost the most per frame. If an application needs more: a `with-fast-slots` macro that looks up each slot's location once (a `gethash` in the class's location table, about 20 ns) and then uses `standard-instance-access`; or inlined accessors per class that check the instance's class and layout and fall back to the generic accessor. Both have to bring an instance up to date after its class is redefined (ECL does that lazily, on the next slot access through the usual paths), and allow for subclasses and mixins that put an inherited slot at another location. Sealing isn't an option: ECL inlines sealed accessors only at `(safety 0)`, and sealing rules out redefinition. Measure with `make bench` (`CLOS: (incf (clos-benchmarks-ticks self))`).
- [ ] **J. Tables keyed by name, updated in place (with the REPL work).** The handle tables (`handle-tables.lisp`) are keyed by `(1+ index)` pointers, and those of classes and methods (`*extension-classes*`, `*bound-methods*`) are append-only. `godot-clos` works around that by registering only what's new when a class is redefined (`godot-registration.lisp`); `define-class` can't be evaluated again at all. Left: key classes and methods by name and update entries in place, in `handle-tables.lisp` (with R). Also, Godot caches `get_virtual_call_data`, so a virtual method a class implements only after Godot first asked isn't called.
- [ ] **AO. Engine methods without the class in their names, and properties as accessors.** An application has to know which engine class defines a method: `(node-2d-set-position mob …)`, `(canvas-item-show message)`, where GDScript says `mob.position = …` and `message.show()`. That's the biggest gap left between Dodge the Creeps and the tutorial's GDScript. Properties could be `setf`-able accessors (`(setf (position mob) …)`), from the `properties` of each class in `extension_api.json`, which `extension-api-json` doesn't read yet. Names that several classes define (`position` in Node2D and Control) need dispatch, e.g. a `typecase` on the structs of the classes that are defined, which is cheap but has to be measured. Names that clash with `cl` (`position`, `get`, `set`, `remove`, `push`) need a rule, such as shadowing in `godot` or a prefix only for those. Keep the prefixed functions for dropping down.
- [ ] **AP. Signals by their Lisp names.** A class declares `(:signals (start-game))`, but emits it with `(object-emit-signal hud "start_game")`, and `after-signal` takes `"timeout"`: names as strings in Godot style, so a typo is found only at run time. `define-signal-emitter` is the fast, checked way, but needs the types a second time (decided on 2026-10-17, see Signal emitters in `CLAUDE.md`), so the game doesn't use it. At least let emitting, connecting and `after-signal` take a symbol in Lisp style, converted to a StringName at compile time (`'start-game`); better, warn at compile or registration time about a name that the class doesn't declare. Revisit `define-godot-signal`, which declares a signal and its emitter in one form, if the double declaration stays the reason emitters go unused.
- [ ] **AQ. Less boilerplate for scenes.** Two things that every scene's code repeats:
  - Every method connected to a signal in the editor needs `(:godot-name "_on_…")`, as the editor names them with a leading underscore. `define-godot-generic` could default a name that starts with `on-` to `_on_…`, so `on-start-button-pressed` is `_on_start_button_pressed`.
  - `(node-get-node hud "Message")` is GDScript's `$Message`, and it's on most lines of a scene's code. A short form, a `$` macro or a reader macro, with the path as a literal NodePath (`npath`).

## Robustness

- [ ] **AR. Check the ECL internals gdecl relies on.** gdecl uses ECL internals: `godot-clos` uses `clos::class-location-table`, `clos::class-size`, `clos::standard-optimized-reader-method`, `clos::standard-optimized-writer-method` and `si::instance-sig-set`, `catching-errors` (`callback/`) binds `si:*handler-clusters*`, and `ffi/` uses `ffi::slot-position`. A new ECL release could change any of them, and gdecl would fail in strange ways, or silently lose fast slot access. Check when gdecl is compiled that they exist and still mean what gdecl expects, and warn about an ECL version other than those tested (24.5.10 so far), saying which internal is missing.

## Gaps

- [ ] **R. Calls from other threads.** Godot calls into Lisp from other threads: Callables on `Thread` and `WorkerThreadPool`, `_process` of nodes in a thread group, instances made by threaded resource loading, objects freed on another thread. `define-callback` already imports and releases threads (`make test` runs Callables on both). Left:
  - The handle tables aren't thread-safe: `vector-push-extend`, `push` and `pop` race, e.g. `callable-free` on a worker thread while the main thread makes a Callable can give two Callables the same index. A lock on every read would cost about 85 ns (an `aref` is 6 ns), too much per frame. Instead, since ECL's GC doesn't move objects, a handle could be the Lisp object's address (1.7 ns to turn back into the object), kept reachable in a table locked only when adding and removing. Do it with J; both change only `handle-tables.lisp`.
  - `*class-name-constructors*` (`engine-objects.lisp`) is filled in by `create-binding`, on any thread: `:synchronized t` (38 ns against 11 ns for `gethash`), or a lock only when filling it in. Never call Godot while holding a Lisp lock: Godot holds its own around `create-binding`.
  - Getting back to the main thread, where most of the scene API must be called: `call-deferred` with a Lisp function, `call-deferred-thread-group`, and wrappers for `WorkerThreadPool`. A REPL (Swank) runs in a thread of its own, so it needs this too.
  - A thread still in Lisp when ECL shuts down isn't waited for.
- [ ] **S. Shipping a game** (low priority for now). An exported game can't load the extension.
  - The `.gdextension` files (the application's and `test/project/`'s) list only `linux.debug`, so a release export has no library; `gdecl.mk` should build one and the README show the `linux.release` entry.
  - `libgdecl.so` links `libecl.so` and `libgc.so` dynamically, so players would need ECL installed: bundle them next to the library (an `$ORIGIN` rpath, and the `[dependencies]` section of the `.gdextension` so Godot exports them), or link ECL statically.
  - Only Linux is built; Windows and macOS need ECL built for them (cross-compiling or CI), and the web would need ECL for Emscripten.
- [ ] **V. More of GDScript in `godot-clos`.** Most of this needs support in `gd-extension`'s registration (`registration.lisp`), then a slot or class option in `godot-clos`. `define-class` gets an option only where that's cheap.
  - `_get`, `_set`, `_get_property_list`, `_property_can_revert`, `_validate_property` and `_to_string` aren't virtual methods in GDExtension but slots of `class-creation-info4` (`get-func` etc.), which `register-class` leaves NULL, so a class can't have dynamic properties. Add callbacks for them like `call-virtual-with-data`'s, and options in both class layers. `define-class` has no option for `_notification` yet.
  - `:export` has no hints: `@export_range`, `@export_enum`, `@export_file`, `@export_multiline`, `@export_flags`, `@export_group`, `@export_category` (`PROPERTY_USAGE_GROUP`). `bind-property` already takes a hint and hint string, so the class layers only need to pass them on.
  - Bound methods have no default arguments (`default-argument-count` is 0), and can't be static (`+method-flag-static+`) or vararg.
  - Classes can't be abstract or virtual (`is-abstract`, `is-virtual`), or have an editor icon (`icon-path`).
  - A Lisp class can't declare virtual methods for GDScript subclasses to override (`classdb_register_extension_class_virtual_method`, and `GDVIRTUAL_CALL` on the Lisp side).
- [ ] **W. Methods of builtin types.** Vector2, Vector3 and Basis have a few functions in Lisp (`types/builtin-types.lisp`); Color, Transform2D, Transform3D, Quaternion, Rect2, AABB, Plane and the integer vectors have only constructors and accessors, so nothing like `Color.lerp`, `Transform2D.basis_xform` or `Rect2.has_point`. The hot ones belong in Lisp, in `gd-extension-builtins`. The rest could be generated like engine methods: a `define-builtin-method` in `godot-generators` (`godot/engine-api.lisp`), on `call-ptr-builtin-method`, which `containers.lisp` already uses. `extension-api-json` already reads the builtin types' methods into `api-method`s, but looks up only their hashes (`api-builtin-method-hash`) so far.
- [ ] **X. Extension points beyond classes.** gdecl starts only at the scene level (`initialize_gdecl_module` in `src/gdecl.c` returns at the other levels). Not possible yet:
  - Editor plugins: classes extending `EditorPlugin`, `EditorInspectorPlugin` or `EditorExportPlugin` must be registered at the editor level and added with `editor_add_plugin`. Needs startup steps per level (`lifecycle.lisp`); ECL is already booted then.
  - Lisp as a script language attached to nodes like GDScript: a `ScriptLanguageExtension` and a `ScriptExtension` (60 and 37 virtual methods) and script instances (`script_instance_create3`). A large piece of work, worth it only if attaching scripts in the editor matters more than defining classes.

## Open questions

- [ ] **AN. Do properties get Variant calls?** Not yet checked: whether Godot calls an extension property's getter and setter with a Variant call, e.g. for `get()`, `set()` or an AnimationPlayer track, which would make that path per frame. Properties have invokers of each type (`signature-invokers`), so it's probably fast enough either way, but measure.
- [ ] **AS. Does `define-class` still pay for itself?** Every feature has to be considered for both class layers (export hints, notifications, singletons), and keeping both makes the README and the tests larger. `define-class` was kept for speed, but `:direct-functions` now makes a `godot-clos` virtual method as fast, and hot data can live in a struct in one slot (AM). What's left in `define-class`'s favor: slot access through struct accessors, and no CLOS at all. Measure a whole game frame both ways; if the difference is small, deprecate `define-class` and keep `godot-clos` with its drop-downs.

## Suggested order

1. AR now, as it's small and protects the CLOS layer from ECL upgrades.
2. AO, AP and AQ, how game code reads, before more speed: the calls between Lisp and Godot are at or near their floor (see Performance in ECL in `CLAUDE.md`). Then V and W as applications need them; V's export hints are the likeliest.
3. J with the REPL work, and R before an application uses threads, including threaded resource loading (`ResourceLoader.load_threaded_request`), which makes instances off the main thread: until then the handle tables can be corrupted.
4. AM when an application's hot code needs faster slot access than a struct gives, and AS, which its measurements help answer.
5. X when there's a reason to extend the editor.
6. S before the first exported game, which doesn't run without it.
